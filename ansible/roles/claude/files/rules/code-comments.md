# コードコメント

コメントにするかどうかは、有用かではなく、その情報が本来どこに属するかで決める。
有用さで決めると「一応書いておく」が積み上がる。置き場所は読み手で決まる。

| 情報                                                                 | 置き場所     |
| -------------------------------------------------------------------- | ------------ |
| なぜこの実装なのか、他案を採らない理由                               | その行の直上 |
| 直感に反する挙動、踏みやすい罠、外部ライブラリの仕様上の制約         | その行の直上 |
| 呼び出し側が守る契約・知るべき前提（解放義務、戻り値の意味、副作用） | doc コメント |
| 変更の経緯（以前はこうだった）                                       | git log / PR |
| 仕様・設計の背景                                                     | README / ADR |
| コードを読めば分かること                                             | 書かない     |

- doc コメントに書くのは、呼び出し側にとっての契約と前提だけである。シグネチャから
  読める概要は書かない。呼び出し側が知る必要がある事実は doc コメントに書き、行の
  直上には重ねない。二重に持つと片方だけ古くなる
- 理由と経緯は過去形で見分ける。過去形を使わずに書き直せるなら現在の設計理由として
  残し、過去形が要るなら経緯として git log へ送る。
  「Worker 間バインディングは公開 URL を経由せず認証プロキシに阻まれない」は理由、
  「CORS で失敗するので Worker 間バインディングに変えた」は経緯である
- 作業ログ（「TODO: 一時的な計測」「後で直す」）は書かない。残すなら issue にする
- 1 つの判断に 1〜3 行。それを超えるなら置き場所が違う。節を分けて段落を重ねたく
  なったら、それは ADR / README の仕事なので、そちらに書いてコメントからリンクする。
  判断の数に上限は無い
