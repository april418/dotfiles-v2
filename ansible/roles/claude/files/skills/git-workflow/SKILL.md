# 概要

このスキルは Git 操作時に **常に意識すべき原則** をまとめたものである。
個別のワークフローではなく、git 関連の作業を行う際の行動規範として機能する。

git コマンドを実行する、または実行しようとするあらゆる場面で以下のルールを遵守すること。

## 場面ごとに読む skill（操作の前に呼ぶ）

この skill は共通ルールだけを持つ。手順の詳細は場面ごとの skill にある。
**以下の場面では、該当する操作を実行する前に、その skill も Skill ツールで呼ぶ。**
Read で SKILL.md を開いただけでは、圧縮の後に本文が戻らない。

| 場面                                                                                                                 | 読む skill               | その skill にあるルール |
| -------------------------------------------------------------------------------------------------------------------- | ------------------------ | ----------------------- |
| 作業ブランチを切る・既存ブランチへ切り替える・ベースを pull する・rebase や stash pop をした後・未コミット変更がある | `git-branch`             | 3, 7                    |
| コミットする                                                                                                         | `git-commit`（ルール 4） | —                       |
| push する                                                                                                            | `git-push`（ルール 5）   | —                       |
| PR を作る・PR をマージする・PR がマージされた直後                                                                    | `git-pr`                 | 11                      |
| `git log <base-ref>..HEAD` に説明できないコミットがある・コンフリクトが起きた                                        | `git-recovery`           | 10                      |

ルール番号は git-workflow / git-branch / git-pr / git-recovery を通した通し番号である。
この skill にあるのは 0, 1, 2, 4, 5, 6, 8, 9。本文に出てくる番号がこの skill に
無ければ、この表で持ち主を引く。

## ルール 0: 非対話時にどこまで進めてよいか

**この規定は `git-*` skill（git-branch / git-pr / git-recovery を含む）全体に効く。**
特定の手順の中だけの話ではない。

非対話（subagent 実行 / CI / Auto Mode 等）では `AskUserQuestion` を呼べない。
確認できないことを理由に停止せず、各ルールが定める既定に沿って進める。
ただし**進めてよい終端は以下で区切る**。

| 操作                                                                                                          | 非対話時                                                   |
| ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 読み取り（`status` / `log` / `show` / `branch --contains` 等）                                                | **常に実行してよい**                                       |
| ローカル操作（`switch` / `cherry-pick` / `stash` / `fetch`）                                                  | **完遂してよい**                                           |
| コミット                                                                                                      | `git-commit` スキルに委譲して実行してよい                  |
| push（通常。追記のみで force を伴わない）                                                                     | `git-push` スキルに委譲して実行してよい                    |
| **ルール 6 の破壊的操作**（force push / `reset --hard` / `rebase` 等）                                        | **実行しない。**選択肢を提示して終える                     |
| `gh pr create` / `gh pr merge` / タグ push / マージ済みのリモートブランチの削除（`git push origin --delete`） | **その操作自体をユーザーが名指ししている場合のみ**実行する |

**この「名指しが必要」は、表の最終行（`gh pr create` / `gh pr merge` /
タグ push / リモートブランチの削除）にだけ係る。** それより上の行は、名指しの
有無で扱いが変わらない（各行の欄に従う）。通常 push を止めない。

最終行の操作に名指しが無いときは、その操作をせずに止まる（PR やタグなら push まで済ませる）。
最終応答に、選択肢・採用理由・次にユーザーが決めるべきことを提示する。
**「進める」を終端の指定なしに解釈して最終行の操作へ踏み込まない。**

### 「名指し」とは何を指すか

**操作種別の名指しであって、対象の完全一致ではない。**
「ツールチップの PR 出して」は `gh pr create` の名指しである。

復旧（git-recovery のルール 10）でブランチ名が変わっても、**同じ作業スコープの成果物である
限り名指しは引き継がれる**。ユーザーが言った名前と違うブランチから PR を
出すことになった場合は、実行してよいが、**採用した名前と理由を最終応答で
明示してユーザーが訂正できる形にする。**

一方、**別の作業スコープの PR やマージには引き継がれない。**
git-pr のルール 11 の承認規律どおり、マージは PR 単位・都度である。

**通常 push を承認不要としている理由**: 作業ブランチへの追記 push は履歴を
書き換えず、後から新しいコミットで打ち消せる可逆な操作だからである。
グローバル指示の承認規律が定める「第三者から観測可能な状態変化」には当たるが、
**不可逆ではない**ためここでは例外として扱う。force を伴う push は
可逆でないのでこの例外に入らず、ルール 6 に従う。

**この表と抽象的な判定基準が食い違って見えたら、この表を優先する。**
git 操作についてはこの表が正本である。

### 要求そのものが多義的で、一方の解釈が破壊的な場合

「整理しておいて」のように、非破壊な解釈（コードを直す）と破壊的な解釈
（履歴を squash する）の両方に読める要求がある。

**非対話では最も非破壊な解釈を既定とする。** 破壊的な解釈は実行せず、
選択肢として提示して終える。推測してよいのは可逆な選択だけで、
不可逆な操作に接続する解釈は推測しない。

**既定の解釈で行う作業が既に済んでいる場合は、追加作業なしで終端に到達したもの
として扱う。** 何かしなければならないと考えて破壊的な解釈に手を伸ばさない。
確認したことと選択肢を報告して終えるのが正しい完了である。

## ルール 1: ブランチモデルは GitHub Flow に従う

扱ってよいブランチは以下のいずれかに限定される。

- **統合ブランチ**: `develop` / `master` / `main`
- **作業ブランチ**: `feature/<name>` / `hotfix/<name>`

それ以外の命名（`fix/xxx`, `chore/xxx`, `topic/xxx` 等）は使用しない。
ユーザーが明示的に別の命名を指示した場合のみ従う。

### `<name>` 部分の命名規約

`feature/<name>` / `hotfix/<name>` の `<name>` 部分は以下に従う。

- **文字種**: ASCII 英小文字 / 数字 / `-` のみ。`_` や空白、日本語は使わない
- **区切り**: `kebab-case`（`user-authentication`、`payment-bug-fix` 等）
- **長さ**: 概ね 3〜40 文字。短すぎ（`x`, `fix`）も長すぎも避ける
- **内容**: 何の作業かが他人に伝わる名詞句（変更対象 + 目的）
  - 良い: `feature/user-authentication`、`hotfix/payment-rounding`
  - 悪い: `feature/work`、`feature/april418-1`、`hotfix/bug`
- **issue 番号がある場合**: 末尾に `-<番号>` を付けてよい（例: `feature/login-form-321`）

### `<name>` の決定主体

デフォルト動作は以下の通り。**推測のまま勝手に決めない**。

1. ユーザーの指示や変更対象から `<name>` を **AI が 1〜3 個提案** する
2. `AskUserQuestion` で候補を提示し、ユーザーに選択 / 修正 / 自由入力させる
3. ユーザーが既に明示的に名前を指定している場合は確認をスキップしてよい

提案できる材料がない場合（指示が極端に抽象的等）は、`AskUserQuestion` で「何の作業をするか」を先に確認する。

**非対話時**は上記の命名規約に沿って自分で決めてよい（ルール 0）。
決めた名前と根拠を最終応答に 1 行明示する。
他のルールが同時に確認を要求している場合も同じで、確認できないことを理由に停止しない。

## ルール 2: 統合ブランチに直接コミットしない

`develop` / `master` / `main` に直接コミット・push してはならない。
作業は必ず `feature/*` または `hotfix/*` ブランチ上で行う。

現在のブランチが統合ブランチのまま変更を加えようとしている場合、
コミット前に `AskUserQuestion` で新しい作業ブランチを切るか確認する。

detach した HEAD（git-pr のルール 11 のマージ直後の追従で `origin/<base>` に detach した後など）
でもコミットしない。rebase / cherry-pick の途中で git が作るコミットは除く（ルール 4 の例外）。
そのコミットはどのブランチにも載らず、別のブランチへ切り替えるとどのブランチからも
辿れなくなる。先に作業ブランチを切る。

## 【重要】ベース参照 `<base-ref>` の定義

**git-branch のルール 3 (b) (c) (d)、git-pr のルール 11、git-recovery のルール 10 は、
すべて同じ参照を使う**（例外は git-pr のルール 11 の遅れの確認と、その rebase 先だけで、
そこは `origin/<base>` を使う。理由はその節にある）。この参照を `<base-ref>` と呼び、git-branch のルール 3 (a) で
選んだベースの所在で決まる。

| (a) で選んだベースの所在                                                                   | `<base-ref>`    |
| ------------------------------------------------------------------------------------------ | --------------- |
| ローカルにあり（`refs/heads/<base>` がある）、ほかの worktree でチェックアウトされていない | `<base>`        |
| リモートにしか無い、またはほかの worktree でチェックアウトされている                       | `origin/<base>` |

ほかの worktree でチェックアウトされているかは次のコマンドで分かる。出力が空か、
今の worktree のパス（`git rev-parse --show-toplevel`）なら、されていない。

```bash
git for-each-ref --format='%(worktreepath)' refs/heads/<base>
```

ほかの worktree でチェックアウトされている `<base>` は、ここからは更新できない。
`git switch <base>` も `git fetch origin <base>:<base>` も exit 128 で拒否される
（`'<base>' is already used by worktree at '<path>'` / `refusing to fetch into branch`）。

**一度決めたら最後まで同じものを使う。** 途中で `<base>` と `origin/<base>` を
混ぜると、リモートのみのケースで `unknown revision` になって落ちる。ほかの worktree に
あるケースでは落ちずに、更新できない古い `<base>` を黙って使う。
以降のコマンド例に出てくる `<base-ref>` はすべてこの値に置き換えて読むこと。

**この分岐は観測結果に従うものであって、選択肢ではない。**
リモートのみだったベースを、わざわざ `git switch <base>` でローカル化して
「ローカルにある側」の手順に乗り換えない。`origin/<base>` のまま最後まで通せる。
ほかの worktree にあるベースも `git switch --ignore-other-worktrees <base>` で切り替えない。
同じブランチを 2 つの worktree でチェックアウトすると、片方でコミットしたとき、もう片方の
index が新しい HEAD とずれ、そのコミットを打ち消す変更がステージされた状態になる。

## ルール 4: コミットは必ず `git-commit` スキルに委譲する

git 操作のうちコミット作成を行う場面では、**自前で `git commit` を実行しない**。
必ず `git-commit` スキルを呼び出す。

対象となる操作:

- 新規コミットの作成
- 既存変更のコミット分割
- コミットメッセージの作成

例外:

- `git commit --amend --no-edit`（メッセージを変更しない単純な amend）
- merge commit / rebase 中の continue 等、git が自動生成するコミット
- ユーザーが明示的に「amend して」「fixup して」等と指示した場合

## ルール 5: push は必ず `git-push` スキルに委譲する

リモートへの push を行う場面では、**自前で `git push` を実行しない**。
必ず `git-push` スキルを呼び出す。

対象となる操作:

- 通常の push
- 初回 push（`-u` 付き）
- 作業ブランチの push

例外:

- ユーザーが明示的に「品質チェックをスキップして push して」と指示した場合
- `git-push` スキル自身の内部処理
- `git push origin --delete`（コミットを送らないので品質チェックの対象が無い。git-pr のルール 11）

## ルール 6: 破壊的操作には必ず確認を取る

以下の操作はすべて `AskUserQuestion` で事前承認を得る。自発的に実行しない。

- `git push --force` / `--force-with-lease`
- `git reset --hard`
- `git clean -fd`
- `git branch -D`（マージされていないブランチの削除）
- `git rebase`（特に push 済みブランチに対するもの）
- `git checkout -- <file>` / `git restore <file>`（未コミット変更の破棄）
- stash の `drop` / `clear`

**列挙は代表例であって網羅ではない。** 判定基準は次の一文である。

> **コミット・未コミット変更・リモートの状態のいずれかを、実行後に復元できない
> 形で失わせうる操作。**

列挙に無いコマンドもこの基準で判定する。たとえば `git switch -C` は、対象
ブランチをチェックアウト中に打つと作業ツリーを書き換えるため、未コミット変更が
あれば**該当する**。無ければ該当しない。**同じコマンドでも状態によって変わる**
ので、コマンド名ではなく「今これを打つと何が失われうるか」で判断する。

統合ブランチ（`develop` / `master` / `main`）への force push は、ユーザーが要求しても行わない（ルール 2。git-push skill は Step 1 で止める）。

## ルール 8: `git merge` は使用禁止、rebase で統合する

`git merge` は使用しない。ブランチの統合は rebase で行う。

- `git pull` は常に `--rebase` を付ける
- 作業ブランチをベースブランチに追従させる場合も `git rebase <base-ref>` を使う
- `git merge` を使ってよいのはユーザーが明示的に指示した場合のみ

```bash
# pull 時は必ず --rebase
git pull --rebase origin <branch>

# ベースブランチへの追従
git rebase <base-ref>
```

コンフリクトが発生した場合の扱いは **git-recovery のルール 10** に集約する
（rebase に限らず cherry-pick / `stash pop` も同じ規律に従う）。

## ルール 9: スコープを逸脱しない

このスキルの対象外の操作は、ユーザーから明示的に要求された場合のみ行う。

- PR の作成（`gh pr create` 等）
- PR のマージ（`gh pr merge` 等）
- タグの作成・push
- リモートの追加・削除
- submodule 操作
- git config の変更

PR の作成とマージを要求された場合は `git-pr` skill のルール 11 に従う。

## チェックリスト

git 操作を行う前に、以下を自問する:

- [ ] 現在のブランチは作業ブランチ（`feature/*` / `hotfix/*`）か？
      （※これは「統合ブランチに直接コミットしない」ための確認。**Yes でも安全とは限らない**。
      作業ブランチ上にいることは、そこから派生すると混入する条件そのものである）
- [ ] この場面で読むべき skill（上の振り分け表）を読んだか？
- [ ] コミットを作る場合、`git-commit` スキルを呼ぶ段取りになっているか？
- [ ] push する場合、`git-push` スキルを呼ぶ段取りになっているか？
- [ ] 破壊的操作の場合、ユーザー承認を得たか？
- [ ] `git merge` ではなく rebase を使っているか？
- [ ] `git pull` に `--rebase` を付けているか？
