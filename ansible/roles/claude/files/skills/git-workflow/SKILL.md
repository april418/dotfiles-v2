# 概要

このスキルは Git 操作時に **常に意識すべき原則** をまとめたものである。
個別のワークフローではなく、git 関連の作業を行う際の行動規範として機能する。

git コマンドを実行する、または実行しようとするあらゆる場面で以下のルールを遵守すること。

## ルール 1: ブランチモデルは GitHub Flow に従う

扱ってよいブランチは以下のいずれかに限定される。

- **統合ブランチ**: `develop` / `master` / `main`
- **作業ブランチ**: `feature/<name>` / `hotfix/<name>`

それ以外の命名（`fix/xxx`, `chore/xxx`, `topic/xxx` 等）は使用しない。
ユーザーが明示的に別の命名を指示した場合のみ従う。

### `<name>` 部分の命名規約

`feature/<name>` / `hotfix/<name>` の `<name>` 部分は以下に従う。

- **文字種**: ASCII 英小文字 / 数字 / `-` のみ。`_` や空白、日本語は使わない
- **区切り**: `kebab-case`（`user-authentication`、`payment-bug-fix` 等）
- **長さ**: 概ね 3〜40 文字。短すぎ（`x`, `fix`）も長すぎも避ける
- **内容**: 何の作業かが他人に伝わる名詞句（変更対象 + 目的）
  - 良い: `feature/user-authentication`、`hotfix/payment-rounding`
  - 悪い: `feature/work`、`feature/april418-1`、`hotfix/bug`
- **issue 番号がある場合**: 末尾に `-<番号>` を付けてよい（例: `feature/login-form-321`）

### `<name>` の決定主体

デフォルト動作は以下の通り。**推測のまま勝手に決めない**。

1. ユーザーの指示や変更対象から `<name>` を **AI が 1〜3 個提案** する
2. `AskUserQuestion` で候補を提示し、ユーザーに選択 / 修正 / 自由入力させる
3. ユーザーが既に明示的に名前を指定している場合は確認をスキップしてよい

提案できる材料がない場合（指示が極端に抽象的等）は、`AskUserQuestion` で「何の作業をするか」を先に確認する。

**非対話時（subagent 実行 / CI 等）**は `AskUserQuestion` を呼べないため、上記の命名規約に沿って自分で決めてよい。決めた名前と根拠を最終応答に 1 行明示する。
他のルールが同時に確認を要求している場合も同じで、確認できないことを理由に停止しない。
ただし**破壊的操作**（ルール 6）だけは非対話でも省略せず、実行せずに選択肢を提示して終える。

## ルール 2: 統合ブランチに直接コミットしない

`develop` / `master` / `main` に直接コミット・push してはならない。
作業は必ず `feature/*` または `hotfix/*` ブランチ上で行う。

現在のブランチが統合ブランチのまま変更を加えようとしている場合、
コミット前に `AskUserQuestion` で新しい作業ブランチを切るか確認する。

## ルール 3: ベースブランチの判定ロジック

新しい作業ブランチを切る手順は **3 ステップ** で行う: **(a) 選定 → (b) 取得・更新 → (c) 派生**。
途中を省略しない。

### (a) ベース選定

1. `git show-ref --verify --quiet refs/heads/develop` が成功する、または
   `git ls-remote --exit-code --heads origin develop` が成功する場合
   → **`develop` から切る**
2. それ以外は `master` または `main` を使用する
   - `main` と `master` の両方が存在する場合は `main` を優先
   - どちらも存在しない場合は `AskUserQuestion` で確認
3. **例外: `hotfix/*` は必ず `master` / `main` から切る**
   - `develop` があっても hotfix では develop を使わない
   - 本番への緊急修正であるため、安定版からの派生が必要

判定は **ローカルとリモートの両方** を確認する。
ローカルに develop がなくてもリモートに存在すればそれを優先する。

`develop` 以外を選ぶときも同じコマンドで存在を確認する。決め打ちしない。

```bash
git show-ref --verify --quiet refs/heads/<候補>
git ls-remote --exit-code --heads origin <候補>
```

### 【重要】ベース参照 `<base-ref>` の定義

以降 **(b) (c) (d) とルール 9 は、すべて同じ参照を使う**。
この参照を `<base-ref>` と呼び、(a) で選んだベースの所在で決まる。

| (a) で選んだベースの所在 | `<base-ref>` |
| --- | --- |
| ローカルに存在する（`refs/heads/<base>` がある） | `<base>` |
| リモートのみに存在する | `origin/<base>` |

**一度決めたら最後まで同じものを使う。** 途中で `<base>` と `origin/<base>` を
混ぜると、リモートのみのケースで `unknown revision` になって落ちる。
以降のコマンド例に出てくる `<base-ref>` はすべてこの値に置き換えて読むこと。

### (b) ベースの取得・更新（派生直前に実施）

選定したベースは **派生直前にリモート最新へ追従させる**。古い HEAD から切ると競合・rebase 苦労の原因になる。

#### 通常ケース（作業ツリーが clean）

```bash
# `<base-ref>` が `<base>` の場合（ローカルに存在）: 一旦 checkout してから rebase pull
git switch <base>
git pull --rebase origin <base>

# `<base-ref>` が `origin/<base>` の場合（リモートのみ）: fetch して直接派生に使う
git fetch origin
```

後者は `refs/remotes/origin/<base>` を用意するための手順である。
(c)(d) がこの ref を参照するので、ここを飛ばすと `unknown revision` になる。
`git fetch origin <base>` のようにブランチを指定すると remote-tracking ref が
更新されるかが refspec 設定に依存するため、**引数なしの `git fetch origin` を使う**。

なお `git pull --rebase` はこの手順が明示的に指示する呼び出しであり、
ルール 6 の要承認操作には**当たらない**（本文が規定する手順として実行してよい）。

#### 例外 1: 作業ツリーに未コミット変更がある場合

まず **ルール 7** で `AskUserQuestion` を出し、3 択のいずれかをユーザーに選ばせる。
選択肢ごとに (b) → (c) の続きが分岐する:

- **「コミットしてから進める」を選んだ場合** → `git-commit` スキルで現ブランチにコミット後、通常ケースに復帰
- **「stash して進める」を選んだ場合**:

  ```bash
  git stash push -u
  git switch <base>
  git pull --rebase origin <base>
  git switch -c <new-branch> <base-ref>   # (c) 派生。ベースを明示する
  git stash pop
  ```

  この場合は (b) 取得・更新を **完遂** する。

- **「そのまま持ち込む」を選んだ場合**:

  ```bash
  git switch -c <new-branch>    # 現在の作業ツリーごと新ブランチへ
  ```

  この場合は **(b) 取得・更新を意図的にスキップ** する（pull を走らせると未コミット変更が衝突するため）。
  ベースは古い HEAD のままになるが、未コミット変更の保護を優先する判断である。新ブランチ上で後ほど `git rebase <base>` で追従可能（ルール 8）。

  **この経路だけはベースを明示しない**（現在の作業ツリーを保持するため、現在の HEAD から切る必要がある）。
  そのため現在のブランチが作業ブランチだと、そのコミットを引き連れる。(d) の検証で必ず確認し、
  混入していたらルール 10 のルート 2（元ブランチを残して cherry-pick）で分離する。

#### 例外 2: オフライン等で fetch / pull が失敗する場合

`AskUserQuestion` で「ローカル HEAD のまま切るか中断するか」を確認する。
「ローカル HEAD のまま切る」を選んだ場合は (b) をスキップして (c) へ。

**非対話時は「ローカル HEAD のまま切る」を採用**し、ベースが古いままである旨を
最終応答に明示する（作業を止めない）。例外 1 も同様に、非対話時は
「stash して進める」を既定とする（未コミット変更を最も安全に保てるため）。

### (c) 派生

更新済みのベースから新ブランチを切る。

**ベースを明示的に指定すること。引数なしの `git switch -c <new-branch>` は使わない。**
引数を省略すると現在の HEAD から切られるため、直前の作業ブランチ上にいた場合に
そのブランチのコミットを引き連れてしまう。

```bash
git switch -c <new-branch> <base-ref>
```

`<base-ref>` は上の定義表で決めた参照（`<base>` または `origin/<base>`）。

### (d) 検証（省略不可）

**派生直後に、余計なコミットを引き連れていないことを確認する。**

```bash
git log --oneline <base-ref>..HEAD
```

**出力が空であること**を確認する。
空でなければ**混入している**。ルール 10 の復旧手順に従う。

この検証が要るのは、(a)〜(c) を守ったつもりで抜けても、
**そのままでは気づけない**ため。ブランチ名も差分も正しく見えてしまう。

実際の事故: 直前の作業ブランチ上にいることを意識しないまま
`git switch -c` を実行し、無関係なコミットを含んだ PR を作成した。
説明文には新しい変更のことしか書かなかったため、
**レビューされないまま別の変更がマージされた**（2026-08-07）。

## ルール 4: コミットは必ず `git-commit` スキルに委譲する

git 操作のうちコミット作成を行う場面では、**自前で `git commit` を実行しない**。
必ず `git-commit` スキルを呼び出す。

対象となる操作:
- 新規コミットの作成
- 既存変更のコミット分割
- コミットメッセージの作成

例外:
- `git commit --amend --no-edit`（メッセージを変更しない単純な amend）
- merge commit / rebase 中の continue 等、git が自動生成するコミット
- ユーザーが明示的に「amend して」「fixup して」等と指示した場合

## ルール 5: push は必ず `git-push` スキルに委譲する

リモートへの push を行う場面では、**自前で `git push` を実行しない**。
必ず `git-push` スキルを呼び出す。

対象となる操作:
- 通常の push
- 初回 push（`-u` 付き）
- 作業ブランチの push

例外:
- ユーザーが明示的に「品質チェックをスキップして push して」と指示した場合
- `git-push` スキル自身の内部処理

## ルール 6: 破壊的操作には必ず確認を取る

以下の操作はすべて `AskUserQuestion` で事前承認を得る。自発的に実行しない。

- `git push --force` / `--force-with-lease`
- `git reset --hard`
- `git clean -fd`
- `git branch -D`（マージされていないブランチの削除）
- `git rebase`（特に push 済みブランチに対するもの）
- `git checkout -- <file>` / `git restore <file>`（未コミット変更の破棄）
- stash の `drop` / `clear`

`main` / `master` への force push をユーザーが要求した場合はリスクを警告する。

## ルール 7: 未コミット変更の扱い

ブランチ切り替え・pull・ベース更新の前には必ず作業ツリーの状態を確認する。

```bash
git status --short
```

未コミット変更がある状態でブランチ切り替えや pull を行おうとする場合、
`AskUserQuestion` で以下を選択させる:

- 現在のブランチでコミットしてから進める（→ `git-commit` スキル）
- stash して進める
- そのまま持ち込む（`git switch -c` 等、安全な場合のみ）

### 選択肢の前提条件（必ず確認）

**現在のブランチが統合ブランチ（`develop` / `master` / `main`）の場合**:
「現在のブランチでコミットしてから進める」は **ルール 2 違反になるため選択肢から除外** する。
残る 2 択（stash / そのまま持ち込む）を提示し、推奨は「そのまま持ち込む」（最短経路、未コミット変更の保護）。

**現在のブランチが既に作業ブランチ（`feature/*` / `hotfix/*`）の場合**:
3 択すべて提示可能。

## ルール 8: `git merge` は使用禁止、rebase で統合する

`git merge` は使用しない。ブランチの統合は rebase で行う。

- `git pull` は常に `--rebase` を付ける
- 作業ブランチをベースブランチに追従させる場合も `git rebase <base>` を使う
- `git merge` を使ってよいのはユーザーが明示的に指示した場合のみ

```bash
# pull 時は必ず --rebase
git pull --rebase origin <branch>

# ベースブランチへの追従
git rebase <base>
```

コンフリクトが発生した場合の扱いは **ルール 10** に集約する
（rebase に限らず cherry-pick / `stash pop` も同じ規律に従う）。

## ルール 9: スコープを逸脱しない

このスキルの対象外の操作は、ユーザーから明示的に要求された場合のみ行う。

- PR の作成（`gh pr create` 等）
- PR のマージ（`gh pr merge` 等）
- タグの作成・push
- リモートの追加・削除
- submodule 操作
- git config の変更

### PR 作成前の内容確認（省略不可）

**`gh pr create` の前に、PR に含まれるコミットを列挙して説明文と突き合わせる。**

```bash
git log --oneline <base-ref>..HEAD
```

`<base-ref>` はルール 3 の定義表で決めた参照。PR の base に指定する予定の
ブランチと同じものを使う（別のブランチと比べると検証の意味がなくなる）。

確認すること。

- **説明文に書いていないコミットが混ざっていないか**
- 意図した変更だけか（ベースの取り違えで無関係なコミットを引き連れていないか）

混ざっていた場合、**そのまま `gh pr create` を実行してはいけない。**
ここで一度止めて、**ルール 10** の復旧手順に従う。

PR 本文には **含まれるコミットを列挙する欄を必ず設ける**。
突き合わせの相手が本文に無いと、この確認は形だけになる。

これが要るのは、ブランチ派生時の取り違えが**PR を出すまで表面化しない**ため。
差分もブランチ名も正しく見えるので、説明文を書いている最中も気づけない。

実際の事故: 直前の作業ブランチから新ブランチを切ってしまい、
無関係なコミットを含んだ PR を作成した。説明文には新しい変更のことしか
書かなかったため、**別の変更がレビューされないままマージされた**（2026-08-07）。
そのマージによって元の PR も自動的に「マージ済み」となり、
レビューの機会が完全に失われた。

### PR マージの承認規律（戦略よりも先に必ず確認）

PR のマージは取り消しが難しく、CI/CD 経由でデプロイまで連鎖しうる操作である。
そのため「マージしてよいか」の判定は以下に従う。

- **承認は PR 単位・都度**: 「マージして」はその発話が指す PR に限る。
  過去の承認や別 PR への承認を流用しない。
- **曖昧な回答は承認ではない**: `AskUserQuestion` の選択肢に対して
  選択肢外の形（素の URL・断片・別話題）で返答が来た場合、それは
  「対象はこれだ」という**情報提供**であり実行承認ではない。
  マージ等の実行前に「この PR をボクがマージしてよいか」を改めて確認する。
- **他人が author の PR は特に慎重に**: AI 自身が作成した PR 以外を
  マージすることは、作者やチームのレビューフローを飛ばす行為になる。
  その PR を名指しした明示要求がない限りマージしない。
- **検証の質は実行権限の代わりにならない**: diff 精読・CI green・
  依存の実在確認をどれだけ丁寧に行っても、無許可マージの正当化にはならない。
  「内容が正しいか」と「実行してよいか」は別の判断である。

背景: 実際に「どう進める？」への回答が PR の URL 提示だけだったのを
推奨案の承認と誤読し、チームメンバー author の PR を無断マージして
デプロイまで発火させ、ユーザーの信頼を損ねた事例がある（2026-07-10）。

※実行系アクション全般（デプロイ・公開・外部送信など git 以外を含む）の
承認原則は CLAUDE.md「曖昧な回答は承認ではない」節が正本である。
本節はその原則を git / GitHub 操作（PR マージ）へ適用した詳細規律の正本である。

### PR マージ時の戦略（明示要求があった場合のみ適用）

ユーザーがマージを要求した場合は **必ず merge commit 形式** を使う。

```bash
gh pr merge <number> --merge
```

`--squash` / `--rebase` は使用しない。理由:

- マージ履歴が残るため、後で「どの PR でこの変更が入ったか」を `git log --first-parent` で辿れる
- 個別コミットの粒度（git-commit skill で revert 可能性最優先に設計したもの）を保てる
- squash は粒度を潰し、rebase は merge commit のメタ情報（PR 番号への参照等）を失わせる

ユーザーが明示的に `--squash` / `--rebase` を指示した場合のみ従う。
`main` / `master` への force push 同様、リスクを警告した上で実行する。

ルール 8（ローカルでの `git merge` 禁止）と矛盾しないこと:

- **ローカルブランチの統合**: `git rebase`（ルール 8）
- **リモート PR のマージ**: `gh pr merge --merge`（このルール）

両者は対象が異なる。

## ルール 10: 混入コミットを見つけたときの復旧（正本）

ルール 3(d) の派生直後の検証と、ルール 9 の PR 作成前の確認は、
どちらも「`git log --oneline <base-ref>..HEAD` に想定外のコミットが出た」
という同じ症状にたどり着く。復旧手順は**この節にだけ書く**。

### まず切り分ける

```bash
git log --oneline <base-ref>..HEAD              # 混入しているコミットの SHA を得る
git branch --contains <混入コミットの SHA>        # 他のブランチにも記録が残っているか
git rev-parse --verify origin/<現在のブランチ>    # push 済みか（成功すれば push 済み）
```

### ルート判定表

| 状況 | ルート | 承認 |
| --- | --- | --- |
| このブランチで**まだ 1 件もコミットしていない** | ルート 1: 切り直し | 不要 |
| 既にコミットした。混入コミットは分離できる | ルート 2: 作り直して cherry-pick | **必須** |
| 既にコミットした。分離できない（依存・衝突する） | ルート 3: 説明文に明記して 1 本で出す | **必須** |

**ルート 2 / 3 の選択はユーザー確認必須。** 混入したコミットが本当に無関係なのか、
他の PR で既に扱われているのかは、こちらからは判断できない。
`AskUserQuestion` で提示する。非対話時はルート 2 を前提に進め、
最終応答で選択肢と採用理由を提示する。

一方 **ルート 1 は確認不要**。失うものが無いため（下記）。

### ルート 1: 切り直し（自分のコミットが 0 件のとき）

**前提条件（必ず先に確認する）**

```bash
git status --short    # 空であること
```

**作業ツリーが clean でなければこのルートを使ってはいけない。**
(d) の直後は対象ブランチを**チェックアウト中**なので、そこへ `-C` を打つと
作業ツリーがベースの内容へ書き換わり、**未コミット変更が失われる**
（`git reset --hard` と同じ結果になる）。
未コミット変更がある場合は先に `git stash push -u` で退避し、
切り直した後に `git stash pop` で戻す。

```bash
git switch -C <new-branch> <base-ref>    # 同名ブランチが既にあるので -c ではなく -C
git log --oneline <base-ref>..HEAD       # 空であることを再確認
```

`-c` は `fatal: a branch named '<new-branch>' already exists` で失敗する。
`-C` は「無ければ作る、あれば指し先を移す」であり、**作業ツリーが clean で
自分のコミットが 0 件**という前提のもとでは失うものがない。
混入コミットも元のブランチから到達可能なまま残る（`git branch --contains` で確認できる）。
この前提を満たす限りルール 6 の要承認操作には該当せず、`git branch -D` も不要。
**前提を満たさないなら該当する**ので、確認を取ること。

**自分のコミットが 1 件でもあるなら `-C` を使わない**（到達不能になる）。
その場合はルート 2 へ。

### ルート 2: 作り直して cherry-pick（推奨）

**`<new-branch>` には元と違う新しい名前を付ける。** 元のブランチは
混入コミットの退避先として残す。名前はルール 1 の命名規約に従い、
`AskUserQuestion` で確認する（非対話時は規約に沿って決め、最終応答で明示する）。

```bash
git switch <base>                        # <base-ref> が origin/<base> の場合はこの行を飛ばす
git pull --rebase origin <base>          #   〃 （代わりに git fetch origin <base>）
git switch -c <別の新ブランチ名> <base-ref>
git log --oneline <base-ref>..HEAD       # 空であること
git cherry-pick <必要なコミット>           # 複数ある場合は古い順に並べる
git log --oneline <base-ref>..HEAD       # 意図したコミットだけになったか再確認
```

既存のコミットを一切壊さず、force push もルール 6 の要承認操作も発生しない。
`cherry-pick` は git が自動生成するコミットなのでルール 4 の例外にあたる
（`git-commit` スキルへの委譲は不要）。

### ルート 3: 説明文に明記して 1 本のまま出す

分離できない場合や、どちらもすぐレビューしてほしい場合に選ぶ。
含まれるコミットを PR 本文に列挙し、**両方がレビュー対象であることを
冒頭で明示する**。

### 選んではいけない対処

現ブランチ上で `git rebase -i <base-ref>` して混入コミットを drop するのは、
最後の手段として以外は選ばない。ルール 6 の要承認操作であるうえ、
push 済みなら force push も必要になり、承認が二重に要る。
さらに、そのコミットが唯一の記録だった場合に別件の作業成果を失う。

### コンフリクトが発生したとき

rebase / cherry-pick / `stash pop` のいずれであっても、
**勝手に `--abort` / `--skip` しない。**
`AskUserQuestion` でユーザーに状況を報告し指示を仰ぐ。
cherry-pick が解けない場合は分離不能ということなので、ルート 3 へ切り替える。

## チェックリスト

git 操作を行う前に、以下を自問する:

- [ ] 現在のブランチは作業ブランチ（`feature/*` / `hotfix/*`）か？
      （※これは「統合ブランチに直接コミットしない」ための確認。**Yes でも安全とは限らない**。
      作業ブランチ上にいることは、そこから派生すると混入する条件そのものである）
- [ ] **ブランチを切る場合、`git switch -c <new> <base-ref>` とベースを明示したか？**
      （引数を省くと現在の HEAD から切られ、直前の作業ブランチのコミットを引き連れる）
- [ ] **派生直後に `git log --oneline <base-ref>..HEAD` が空であることを確認したか？**
- [ ] **PR を作る前に `git log --oneline <base-ref>..HEAD` を説明文と突き合わせたか？**
      （書いていないコミットが混ざったまま出すと、レビューされずにマージされる）
- [ ] コミットを作る場合、`git-commit` スキルを呼ぶ段取りになっているか？
- [ ] push する場合、`git-push` スキルを呼ぶ段取りになっているか？
- [ ] 破壊的操作の場合、ユーザー承認を得たか？
- [ ] 未コミット変更の扱いは明確か？
- [ ] `git merge` ではなく rebase を使っているか？
- [ ] PR をマージする場合、**その PR を名指しした明示要求**があるか？
      （曖昧な回答・URL 提示だけでは承認ではない。他人 author の PR は特に）
- [ ] PR マージ時は `--merge`（merge commit）を使っているか？
- [ ] `git pull` に `--rebase` を付けているか？
