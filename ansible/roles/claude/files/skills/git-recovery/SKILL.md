# 概要

混入コミットの復旧とコンフリクト時の扱いをまとめる。共通ルール（非対話時の終端、
命名規約、破壊的操作の承認、`<base-ref>` の定義）は `git-workflow` skill にある。

このファイルにあるルールは 10 だけである。ほかの番号は `git-workflow` の振り分け表で
持ち主を引く。

## ルール 10: 混入コミットを見つけたときの復旧（正本）

git-branch のルール 3(d) の派生直後の検証と、git-pr のルール 11 の PR 作成前の確認は、
どちらも「`git log --oneline <base-ref>..HEAD` に想定外のコミットが出た」
という同じ症状にたどり着く。復旧手順は**この節にだけ書く**。

### 【重要】出力が空でない = 混入、ではない

**空を期待してよいのは派生直後（3(d)）だけである。**
作業が進んだブランチでは空でないのが正常で、そこで空を期待すると誤検知する。
git-pr のルール 11 の合格条件は「空」ではなく「説明文と一致」である。

派生直後**以外**の文脈でこの節に入るときは、まず下の切り分けで
**混入が本当にあるのか**を確かめる。自分で作ったコミットが並んでいるだけなら
復旧ルートは 1 つも発動しない。**正常なコミットを cherry-pick で分解しない。**

### まず切り分ける

```bash
git status --short                              # 作業ツリーが clean か（ルート 1 の前提）
git log --oneline <base-ref>..HEAD              # 混入しているコミットの SHA を得る
git branch --contains <混入コミットの SHA>        # 他のブランチにも記録が残っているか
git rev-parse --verify origin/<現在のブランチ>    # push 済みか（成功すれば push 済み）
```

**「自分のコミット」の数え方**: ルート判定でいう件数は、**この作業で自分が
作ったコミット**の数である。引き連れてしまった混入コミットは元から他ブランチに
あったものなので数に入れない。`git branch --contains` の出力に**現在のブランチ
以外**が並ぶなら、それは引き連れた側である。

ただし引き連れ元のブランチが既に削除されていると、混入コミットでも現在の
ブランチしか返さない（偽陰性）。判定の軸はコマンド出力ではなく
**この PR / 作業に入れたいコミットかどうか**である。出力が判断と食い違ったら、
`git show --stat` で内容を見て、今の作業のスコープに属するかで決める。

### ルート判定表

| 状況 | 判定方法 | ルート | 承認 |
| --- | --- | --- | --- |
| **混入コミットが 0 件**（並んでいるのは全部自分のもの） | 上の切り分け | **どのルートも発動しない。何も変更せず、ここで完了**。検証結果だけ報告する | 不要 |
| 自分のコミットが **0 件**（かつ作業ツリー clean） | 上の切り分け | ルート 1: 切り直し | 不要 |
| 自分のコミットが 1 件以上。混入コミットは分離できる | 下記の分離可能性チェック | ルート 2: 作り直して cherry-pick | **必須** |
| 自分のコミットが 1 件以上。分離できない | 同上で「不可」と出た場合 | ルート 3: 説明文に明記して 1 本で出す | **必須** |

#### 分離可能性のチェック（ルート 2 / 3 の分岐）

推測で決めない。まず変更ファイルの重なりを見る。

```bash
git show --stat --oneline <混入コミット>
git show --stat --oneline <残したいコミット>
```

**変更ファイルが重なっていなければ分離できる**（ルート 2）。
重なっている場合は cherry-pick が衝突しうるので、実際に試して判定する。

**この分岐は可逆である。** 迷ったらルート 2 を暫定選択してよい。
cherry-pick が衝突したら分離不能ということなので、`--abort` を打って
ルート 3 へ切り替える。**判定に迷って止まるより、試して切り替える方がよい。**

#### 承認と、非対話時にどこまで進めてよいか

**ルート 2 / 3 の選択はユーザー確認必須。** 混入したコミットが本当に無関係なのか、
他の PR で既に扱われているのかは、こちらからは判断できない。
`AskUserQuestion` で提示する。

**ルート 1 は確認不要**（前提を満たす場合のみ。下記）。

非対話時はルート 2 を前提に進める。ただし進めてよい終端は
**git-workflow のルール 0「非対話時にどこまで進めてよいか」** に従う。
PR の作成を名指しされているなら、ルート 2 で作った新ブランチから PR まで進めてよい
（名指しは同じ作業スコープの成果物に引き継がれる）。その前に、新ブランチで
git-pr のルール 11 の内容確認をやり直す。名指しが無ければ push まで済ませて止まる。

### ルート 1: 切り直し（自分のコミットが 0 件のとき）

**前提条件（必ず先に確認する）**

```bash
git status --short    # 空であること
```

`<base-ref>` が `origin/<base>` の場合、**この節から直接入ってきたなら
まだ ref が無いことがある**（git-pr のルール 11 経由や、git-branch のルール 3 (a)〜(c) を
飛ばして事故った場合）。先に git-branch のルール 3 (b) の取得・更新を済ませること。
済んでいないと `unknown revision` で落ちる。

**作業ツリーが clean でなければこのルートを使ってはいけない。**
git-branch のルール 3 (d) の直後は対象ブランチを**チェックアウト中**なので、そこへ `-C` を打つと
作業ツリーがベースの内容へ書き換わり、**未コミット変更が失われる**
（`git reset --hard` と同じ結果になる）。
未コミット変更がある場合は先に `git stash push -u` で退避し、
切り直した後に `git stash pop` で戻す。

```bash
git switch -C <new-branch> <base-ref> --no-track   # 同名ブランチが既にあるので -c ではなく -C
git log --oneline <base-ref>..HEAD                 # 空であることを再確認
```

`-c` は `fatal: a branch named '<new-branch>' already exists` で失敗する。
`-C` は「無ければ作る、あれば指し先を移す」であり、**作業ツリーが clean で
自分のコミットが 0 件**という前提のもとでは失うものがない。
混入コミットも元のブランチから到達可能なまま残る（`git branch --contains` で確認できる）。
この前提を満たす限り git-workflow のルール 6 の要承認操作には該当せず、`git branch -D` も不要。
**前提を満たさないなら該当する**ので、確認を取ること。

**自分のコミットが 1 件でもあるなら `-C` を使わない**（到達不能になる）。
その場合はルート 2 へ。

### ルート 2: 作り直して cherry-pick（推奨）

**`<new-branch>` には元と違う新しい名前を付ける。** 元のブランチは
混入コミットの退避先として残す。名前は git-workflow のルール 1 の命名規約に従い、
`AskUserQuestion` で確認する（非対話時は規約に沿って決め、最終応答で明示する）。

```bash
# ベースの取得・更新は git-branch のルール 3 (b) に従う（<base-ref> で分岐する。ここには再掲しない）
git switch -c <別の新ブランチ名> <base-ref> --no-track
git log --oneline <base-ref>..HEAD       # 空であること
git cherry-pick <必要なコミット>           # 複数ある場合は古い順に並べる
git log --oneline <base-ref>..HEAD       # 意図したコミットだけになったか再確認
```

既存のコミットを一切壊さず、force push も git-workflow のルール 6 の要承認操作も発生しない。
`cherry-pick` は git が自動生成するコミットなので git-workflow のルール 4 の例外にあたる
（`git-commit` スキルへの委譲は不要）。

**復旧後に残る中間物の扱い**: 元のブランチは**削除しない**。混入コミットが
そこにしか無い可能性があり、`git branch -D` は git-workflow のルール 6 の要承認操作である。
残したまま最終応答で「元のブランチに何が残っているか」を伝え、
その後どうするかはユーザーに決めてもらう。

### ルート 3: 分離せず 1 本のままにする

分離できない場合や、どちらもすぐレビューしてほしい場合に選ぶ。

**このルートのローカル到達点は「何も変更しない」である。** 履歴もブランチも
そのままにする。やることは、混入コミットも一緒に扱うと決めた事実を残すこと
だけである。

その先で PR を出すなら、含まれるコミットを本文に列挙し、**両方がレビュー対象で
あることを冒頭で明示する**。ただし PR 作成自体は git-workflow のルール 0 の終端表に従う
（ユーザーが名指ししていなければ実行しない）。

**PR を出さない文脈でこのルートに至った場合は、それで完了である。**
何も実行せず、分離できなかった事実と 2 件が同居していることを最終応答で伝える。

### 選んではいけない対処

現ブランチ上で `git rebase -i <base-ref>` して混入コミットを drop するのは、
最後の手段として以外は選ばない。git-workflow のルール 6 の要承認操作であるうえ、
push 済みなら force push も必要になり、承認が二重に要る。
さらに、そのコミットが唯一の記録だった場合に別件の作業成果を失う。

### コンフリクトが発生したとき

対話時は、rebase / cherry-pick / `stash pop` のいずれであっても、
**勝手に `--abort` / `--skip` しない。**
`AskUserQuestion` でユーザーに状況を報告し指示を仰ぐ。
cherry-pick が解けない場合は分離不能ということなので、ルート 3 へ切り替える。

#### 非対話時の既定

| 衝突した操作 | 非対話時の既定 |
| --- | --- |
| ルート 2 の cherry-pick | `git cherry-pick --abort` で始める前に戻し、元のブランチへ切り替えて止まる |
| それ以外（rebase / `stash pop` / ルート 2 以外の cherry-pick） | **衝突した状態のまま止まる** |

`git cherry-pick --abort` は、その cherry-pick コマンドで取り込んだコミットをすべて外す
（衝突より前に取り込めたものも外れる）。ルート 2 で作ったブランチは消さずに残し、最終応答で伝える。
元のブランチはルート 3 のローカル到達点と同じ状態だが、ルート 3 は承認が要るので、
PR の作成を名指しされていても混入コミットを含んだ PR は作らない。

「衝突した状態のまま止まる」とは、`--abort` / `--skip` / `--continue` / `--quit`、衝突を解くための編集と `git add`、
stash の `drop` のどれもしないことである。どちらの変更を残すかは変更の意図で決まり、
こちらからは判断できない。衝突が残っている間は `git switch` も `git commit` も失敗するので、
後続のコミットや push も行わない。どちらの行も、git-workflow のルール 0 の表の
「選択肢を提示して終える」と同じ終え方をする。

最終応答には次を書く。衝突したファイルは `git diff --name-only --diff-filter=U` で取る。
ルート 2 の cherry-pick では `--abort` の後は空になるので、その前に控える。

- 衝突した操作と、衝突したファイル
- 衝突したまま止まった rebase / cherry-pick なら、解いて `--continue` するか、`--abort` で始める前に戻すか
- `stash pop` なら、退避したときのメッセージ。衝突しても stash は消えずに残っている。
  衝突しなかった変更は適用済みで、追跡ファイルはステージされ、未追跡ファイルは未追跡のまま戻っている。
  解いた後に drop するかは、git-workflow のルール 6 に従ってユーザーが決める
- ルート 2 の cherry-pick なら、残したルート 2 のブランチ名と、選択肢（混入コミットを含めて
  1 本で出すルート 3 か、手で解いて分離するか）
