# slide-writing

スライドの中身を作る手順である。システム側のスライドの skill（Artifact の Slides の type、
pptx の skill など）に重ねて使う。

| 決めること                                                                 | 従うもの                     |
| -------------------------------------------------------------------------- | ---------------------------- |
| 結論、読者、ストーリーの流れ                                               | この skill                   |
| 見出しの書き方、Abstract                                                   | この skill                   |
| 持ち時間と枚数、根拠を図表と文のどちらで見せるか、図表の種類、1 枚の文の量 | この skill                   |
| 文字の大きさ、配色、書体                                                   | システム側のスライドの skill |
| レイアウト、ファイルの形式と書き出し方                                     | システム側のスライドの skill |

システム側も見出しや構成に指示を持つことがある（Slides の type は見出しを話題にするよう言う）。
上の表でこの skill の行に当たるものは、この skill に従う。

工程は下の 8 つで、この順に踏む。前の工程が決まらないまま次へ進まない。結論が無いまま
本文を書くと、スライドは情報の羅列になり、読み終えた人が何を持ち帰ればよいか分からない。

工程 1〜6 は、システム側でデッキを作り始める前に、下書き（会話の中か scratchpad のファイル）で
済ませる。工程 3 の流れはシステム側の outline（Slides の type の `sections`）に、工程 4 の見出しは
各スライドの見出しにそのまま使う。システム側が「仮定を 1 行言って進む」と言っても、工程 1・2 の
確かめ方はこの skill に従う。工程 8 の修正は、システム側の改訂の手順で反映する。

`AskUserQuestion` が無い環境（Codex など）では、同じ候補を本文の問いで出し、答えを待つ。

## 1. 結論を決める

読み終えた人に持ち帰ってほしいことを、一文で書く。主語と述語のある文にし、題目
（「新しい CI について」）にしない。

- 結論は依頼者のものである。依頼の文面や渡された資料から読み取れなければ、候補を 2〜3 個
  作って `AskUserQuestion` で選んでもらう
- 一文に収まらないなら、伝えたいことが複数ある。1 つに絞るか、デッキを分けるかを依頼者に聞く
- 読み終えた人にしてほしい行動（承認する、試す、覚えておく）があれば、結論と並べて書く

## 2. 対象読者を考える

結論を届ける相手を具体的にする。次を書き出す。

- 誰か（役割、人数、聴く場か配られて読むだけか）
- すでに知っていることと知らないこと。説明なしで通じる用語の範囲
- 結論を聞く前に抱いていそうな考えや疑問、反対しそうな点
- 読むか聴くか（聴くならスライドの文字を減らし、話す内容を発表者ノートに置く）
- 聴く場なら持ち時間。依頼者が言わなければ 10 分程度とし、聞かずに進める。時間を言われたら、
  それに合わせる。枚数は表紙と Abstract を除いて 1 枚 1 分で見積もり、10 分なら 8〜10 枚に
  収める。1 分は、見出しを読み上げて根拠を 1 つ説明するのにかかる時間の目安である

読者が依頼から分からなければ、結論と一緒に `AskUserQuestion` で聞く。ここで決めた読者像は
工程 7 のレビューでそのまま使う。

## 3. ストーリーの流れを考える

結論に読者を連れていく順番を決める。起承転結を下敷きにし、スライド 1 枚ごとに 1 行の
メモを並べる。表紙と Abstract はこのメモに入れない。

| 段  | 置くもの                                                             |
| --- | -------------------------------------------------------------------- |
| 起  | 読者への問い 1 枚。表紙の直後、Abstract の前に置く                   |
| 承  | 読者がいま抱えている状況と、問いを深める事実、データ、これまでの試み |
| 転  | 結論を根拠と一緒に示し、読者の見方を変える                           |
| 結  | 問いへの答えとしての結論の言い直しと、読者にしてほしい行動           |

起の問いは、読者が自分の経験や手元の数字で答えられるものにする（「あなたの CI は 1 回
何分かかっていますか」）。読者は答えを考えた時点で、続く話を自分の話として聞く。題材の
一般論（「CI は速いほうがよいでしょうか」）は、答えが決まっていて考える余地が無いので
避ける。問いへの答えが工程 1 の結論につながることを確かめ、結でその問いに答える。

並べたら、次の 3 つの場所を決めてメモに印を付ける。

- 盛り上がり: 流れの山を 1 か所に決める。多くは転である。山が複数あると、どれも山に見えない
- 笑いをとる場所: 起や承の、読者の緊張をほどきたいところに置く。結論の直前と、失敗や損失を
  扱うスライドには置かない。笑いの後は読者の気がゆるみ、続く主張が軽く聞こえる。障害の
  振り返りのように題材や読者に合わないデッキでは、置かないと決めてそう書く
- 真剣に・熱く伝えたい場所: 結論と、読者に行動を頼むところに置く。ここは言葉を飾らず、
  短く言い切る

工程 1・2 の結論か読者を推測で決めたときは、工程 4 に進む前に、結論・読者・流れを
`AskUserQuestion` で依頼者に確かめる。本文を書いた後に結論が違うと分かると、流れごと
書き直すことになる。依頼者に聞けない場面（非対話）では確かめずに進め、推測したことを
最後の報告に書く。工程 2 の既定の持ち時間は、この確認に入れず、報告に書くだけにする。

## 4. 見出しと Abstract を考える

本文より先に、全スライドの見出しと Abstract を書く。

- 見出しは、そのスライドの主張を文で書く（「ビルド時間は 3 分の 1 になった」）。題目
  （「ビルド時間」）にしない。起の 1 枚だけは、見出しを工程 3 の問いにする。見出しだけを
  上から読んで、ストーリーが通ることを確かめる
- Abstract は起の問いの次に置く 1 枚で、結論と、そこに至る理由を 3 行以内で書く。最後まで
  聴けない人も、ここで結論を持ち帰れる
- 結論が出るのは Abstract・転・結の 3 か所で、役目を分ける。Abstract は先に言う、転は根拠と
  一緒に納得させる、結は言い直して行動を頼む
- 表紙と Abstract を除いた見出しが、工程 3 のメモと 1 対 1 で対応しているかを見る。対応しない
  スライドは流れに無いことを話しているので、消すか流れを直す

## 5. 本文を書く

見出しの主張を支えるものだけを、各スライドに置く。

- 1 枚に主張は 1 つにする。2 つ目の主張が出たら、スライドを分ける
- 主張を支える根拠（数字、図、例）を選ぶ。見出しを支えない情報は、正しくても置かない
- 根拠は図表で見せ、文はその図表を読むための一言にとどめる。数字の比較や推移はグラフ、
  項目の対応は表、仕組みや順序は図解、画面や実物は画像にする。聴き手は話を聞きながら
  文を読み切れず、配られて読む人も流し読みするが、図表なら一目で形をつかめる。文だけで
  よいのは、起の問い・Abstract・結の言い切りのように、一言を大きく見せるスライドである
- 画像は、依頼者が渡したものとシステム側のスライドの skill が使ってよいとするものだけを
  使う。作った画面や出どころの分からない画像は、実物と見分けがつかず、読者が事実と取り違える。
  使える画像が無ければ図解で代えるか、依頼者に画像をもらう。どちらもできなければ
  「[画像: 設定画面の環境変数の欄]」のように置き場所だけを示し、最後の報告に書く
- グラフの形と描き方は、dataviz の skill があればそれに従い、配色はシステム側のスライドの
  skill に合わせる
- 工程 2 の読者が知らない用語は、初めて出たスライドで説明するか、言い換える
- 数字、日付、名前は出典で確かめてから書く
- 聴く場なら、話す内容は発表者ノートに書き、スライドには要点だけを残す

## 6. 通して読み、推敲する

全スライドを最初から最後まで、工程 2 の読者のつもりで読む。

- 見出しだけを続けて読み、ストーリーが通るか
- 盛り上がり・笑い・熱く伝える場所が、工程 3 で決めた位置にあり、その役目を果たしているか
- Abstract・転・結のほかで、同じことを繰り返していないか
- 起の問いに、結が答えているか
- 文だけのスライドが、工程 5 で文だけにしてよいとしたものと、画像の置き場所だけを示したもののほかに無いか
- 図表に添えた文が一言を超えていないか
- 持ち時間に収まるか（聴く場なら、表紙と Abstract を除いた枚数を 1 枚 1 分で概算する）
- 日本語のスライドは、グローバル指示の「手順を持つ skill」が決める順で文面を推敲する

## 7. 別のエージェントにレビューを頼む

書いた本人は結論を知っているので、伝わっていない箇所に気づけない。結論を知らない
エージェントに、想定読者になりきって読んでもらう。

fork ではない新しい subagent を 1 体だけ起こす（Claude Code の Agent ツールでは
`subagent_type` を省く）。渡すのは次の 2 つだけである。

- 工程 2 の読者像（誰で、何を知っていて、何を知らないか）。「この人になりきって読む」と指示する
- スライドの全文。見出し、本文、発表者ノートをスライド順に並べ、図や画像は「[図: 棒グラフ。
  横軸 1〜6 月、縦軸ビルド時間（分）。値は 12, 12, 11, 6, 4, 4]」のように、描いてあるもの
  （軸、系列、値、ラベル）だけで書き起こす。読み取ってほしいこと（「4 月から下がる」）を
  書くと、図表から読み取れるかを確かめられない

工程 1 の結論と工程 3 の意図は渡さない。渡すと、レビューはそれが伝わったかではなく、
それに沿っているかの確認になる。指示には次の制約を書く。

- 渡した本文のほかのファイル、Artifact、会話記録を読まない（下書きに結論が書いてある）
- 口調は問わず、下の項目ごとに答える

返してもらうものは次のとおりにする。

- このデッキが言いたいことを一文で。そして、それに納得したか、納得したのはどのスライドで、
  納得できなかったのはどのスライドか
- 読者として、してみようと思ったこと
- 起の問いに自分ならどう答えるか。答えを考えられたか
- 分からなかった用語や、話についていけなくなったスライド（番号と理由）
- 図表を見ても言いたいことが分からなかったスライド（番号と、図表から読み取ったこと）
- 退屈したスライド、笑えたかどうか、熱が伝わったスライド
- 読者として反論したくなった箇所

Abstract が結論を言うので、一文が工程 1 の結論と合うのは当然である。見るのは、納得の根拠に
転のスライドが挙がっているかと、納得できなかったスライドがどこかである。

Agent ツールのように新しい文脈の subagent を起こせない環境では、この工程を飛ばし、飛ばしたことと
理由を最後の報告に書く。

## 8. 修正する

レビューの指摘を、どの工程を直せば解けるかで分ける。

| 指摘                                   | 直す工程                                    |
| -------------------------------------- | ------------------------------------------- |
| 一文が結論と違う、転で納得していない   | 工程 3 の流れと工程 4 の見出し              |
| ついていけない、用語が分からない       | 工程 5 の本文（説明を足す、言い換える）     |
| 問いに答えられない、自分の話に思えない | 工程 3 の起の問い                           |
| 図表が読めない                         | 工程 5 の図表の選び方と、添える一言         |
| 退屈、笑えない、熱が伝わらない         | 工程 3 の印の位置と、そのスライドの工程 5   |
| 反論が出る                             | 工程 5 で承に根拠を足すか、結で反論に答える |

指摘は読者像の一人の反応なので、全部を採るとは限らない。採らなかった指摘は理由を控えておく。
直したスライドは、工程 6 の通し読みと推敲をもう一度通す。

一文が結論と違うか、転で納得していなかったときだけ、直した後に工程 7 をもう一度流す。
工程 7 は最初の 1 回を含めて 2 回までにする。もう一度流すときも新しい subagent を起こし、
前のレビューの内容は渡さない。2 回目でも合わなければ 3 回目は流さず、食い違いを依頼者に
報告して、結論か読者像を決め直すかを聞く。

## 報告するもの

デッキを渡すときに、次を添える。

- 工程 1 の結論と工程 2 の読者像。推測で決めたなら、そう書く
- 持ち時間を既定の 10 分にしたなら、そのことと枚数
- 画像の置き場所だけを示したスライドと、要る画像
- レビューで返ってきた一文と、納得の根拠に挙がったスライド
- 採らなかった指摘と理由。工程 7 を飛ばしたなら、そのことと理由
