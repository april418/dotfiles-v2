# 概要

ユーザー本人が書いたように読める PR のコメントを書くためのルールである。
2023-04〜2026-03 にユーザーが手で書いた次のコメントから抽出した。
以降は AI を併用しているため対象に含めていない。

- **他者の PR へのレビュー**: 633 件（レビュー本文 306・インライン 262・会話欄 65）と、同期間のレビュー状態
- **自分の PR で作者として書いたもの**: 706 件（レビュアーへの返信 388・自分から付けた補足 318）

| 文章 | このスキル |
| --- | --- |
| 他者の PR への Approve / Comment の本文 | 使う |
| 他者の PR へのインラインコメント・suggestion | 使う |
| 他者の PR のレビュースレッド・会話欄への返信 | 使う |
| 自分の PR でレビュアーに返す文・自分から付ける補足 | 使う（ルール 10） |
| コミットメッセージ・PR 本文 | 使わない（グローバル指示どおり常体） |
| Issue・チャット・メール・ユーザーへの応答 | 使わない |

- レビューコメントはユーザー本人の発話として書くため、グローバル指示の
  「成果物は常体」の対象外とし、このスキルの口調で書く
- ずんだもんの口調は一切混ぜない
- このスキルは文面を決めるだけで、投稿の許可にはならない。GitHub への投稿は
  グローバル指示の承認規律に従う

## ルール 1: レビュー状態は推奨として示し、決めるのはユーザー

**Approve を自分の判断で付けない。** Approve はブランチ保護の必須レビューを満たし、
auto-merge が有効ならそのままマージまで進む。

- 投稿の承認を求めるときは、本文と推奨する状態を並べて示す
- Approve は、ユーザーが状態まで名指しして承認したときだけ付ける
- 対象 PR の auto-merge の有無（`gh pr view <番号> --json autoMergeRequest`）を承認確認に添える

推奨する状態はユーザーの実績に合わせる。実績は APPROVED 287 件、COMMENTED 87 件
（スレッドへの返信だけのものを除く）、CHANGES_REQUESTED 0 件である。

| 状況 | 推奨する状態 |
| --- | --- |
| 指摘なし | Approve。本文は「LGTM!」だけ |
| 細かい指摘だけ、または相手に任せられる小さな修正がある | Approve ＋ インライン。条件付きなら本文に一文添える |
| 確かめた範囲は問題ないが、一部は判断できない | Approve ＋ 判断できない部分を本文に書く |
| 直った後にもう一度見たい、回答次第で判断が変わる | Comment。本文なしでインラインだけ付けるのが最も多い（87 件中 67 件） |
| 妥当性をまったく判断できない | Comment ＋ その旨を本文に書く |

**Request changes は使わない。** ユーザーが明示的に求めた場合だけ例外とする。

## ルール 2: 指摘は「提案」と「質問」で出す

- 命令形で書かない。依頼は「〜した方がいいかもです」「〜してもらえると助かります！」
  「〜お願いできますか！」の形にする
- 「〜してください」を使うときは、末尾を「〜」「！」「…」「🙇」で和らげる
- 相手に意図があった可能性を先に聞く。決めつけて直させない
- 自分の誤解の可能性があるときは書き添える（「コードだけ見て書いてるので間違ってたらすみません！」）

## ルール 3: 確度は実際に確かめた度合いに合わせる

口調が柔らかいことと、事実をぼかすことは別である。**口調は指摘の重さの判断を変えない。**

- 確かめたことは確かめたと書く（「手元で空配列渡したら落ちました…！」）
- 確かめていないことにだけ「〜気がします」「〜かもです」を使う
- 「間違ってたらすみません」は本当に確かめていないときだけ書く。確かめた不具合に付けない

## ルール 4: 指摘の重さはラベルではなく前置きで伝える

`nit:` `[must]` `Suggestion:` のようなラベルは付けない。1 文目の前置きで重さを示す。

| 重さ | 前置きの例 |
| --- | --- |
| ごく軽い・好み | 「細かいですが」「すごい細かいんですが」「好みの問題ではあるんですが、個人的には」「超どうでもいい話なんですけど」 |
| 念のため | 「念のためレベルの話なんですが」「（念のため）」 |
| スコープ外 | 「このプルリクでやらなくて大丈夫なんですが」「全然今回の変更関係ないですけど」「元からっぽいんですが」 |
| 純粋な興味 | 「単純な興味ですが」「ただ気になるってだけなんですが」 |
| 直してほしい | 前置きなしで結論から書く。「〜で落ちます…」「〜だとダメそう？」 |

スコープ外の指摘は対応するかを相手に委ねる。
「（このプルリクではやらなくて大丈夫）」「どこまでこのプルリクで直すかはお任せします！」

## ルール 5: 提案・依頼・推測の文末は言い切らない

ベースは「です・ます」で、提案・依頼・推測は断定せず柔らかく終える。
確かめた事実はルール 3 のとおり言い切ってよい。

**行末に「。」はほぼ付けない。** 実績では行末の 37% が記号なし、17% が「！」、
15% が「）」、9% が「…」で、「。」は 7% しかない。全文を「。」で終えると
それだけで別人の文になる。

よく使う文末:

- 「〜気がします」「〜気がしました」「〜と思います」「〜と思いました」
- 「〜ですかね？」「〜感じですかね？」「〜たりします？」「〜ありますっけ？」
- 「〜かなと（思います）」「〜いいかなと！」「〜かもです」「〜かもですね」
- 「〜良さそうです」「〜っぽいです」「〜ですね」「〜んですよね」
- 相手を安心させるときは「〜ですよ！」「〜っすよ」（「それでも全然OKですよ！」）
- 同意を求めるときは「〜ですよね？」

**言いさし**（文を途中で止める）が多い:

- 「〜してもらえると！」「〜できるかと！」「〜した方がいいかなと」「〜みたいな」
- 理由の補足は「〜ので」で止める（「先にイベントが発火しちゃう可能性があるので」）

砕けた形はアクセントとして少量だけ使う（「っす」は全コメントの 4%、関西弁は 1% 未満）:

- 「〜っす」「〜っすね」「そっすね」「なるほどっす」「あざっす！」
- 独り言調の「〜なのか…」「なるほどなあ…」「〜かあ」
- ツッコミでまれに関西弁（「ほんまや…！」「〜やん…」）

使わないもの:

- 「〜でございます」「〜いただけますでしょうか」「ご検討ください」
  「ご確認のほどよろしくお願いいたします」
- 相手に向けた「〜だよ」「〜だね」「〜じゃん」（実績 0 件。独り言の「〜んだよなあ…」はある）
- 「〜のだ」

## ルール 6: 一人称・呼び方・語彙

- 一人称は「わたし」（ひらがな）が多く、次いで「私」
- メンションは `@id san`（半角スペースを挟んで san）
- 他のレビュアーに向けた補足は「（主に他のレビュワーさん向け）」と断る
- PR は「プルリク」と呼ぶ
- 程度の言葉は「ちょっと」「めっちゃ」「結構」「若干」
- 良い評価は「良さそう」「良さげ」「いい感じ」「キレイ」「すっきり」「イケてる」

## ルール 7: 記号と絵文字

| 記号 | 頻度の目安 | 使いどころ |
| --- | --- | --- |
| ！ | 6 割のコメント | 提案・お礼・LGTM の文末を明るくする |
| … | 2 割 | 自信がない・申し訳ない・困っているときの文末 |
| （ ） | 1.5 割 | 本文の次の行に理由・前提・自虐・脱線を置く（下記） |
| w | 5% | 軽いツッコミや自虐の文末。重い指摘には付けない |
| 🙇 | 3% | 謝罪・お礼・お願い |
| 👍 😇 🙆 など | まれ | 褒め・諦め・OK。1 コメントに 1 個まで |
| ~~取り消し線~~ | まれ | 書きながら自分の誤りに気づいたとき（「~~〜~~ あ、〜なのか。失礼。」） |

- 「！」の後に同じ行で文を続けるときは全角スペースを挟む（「あざっす！　LGTM！」）
- 「!」と「！」、全角と半角の括弧は混在してよい。揃えすぎない

**括弧の補足**はこの口調の最大の特徴である。本文を言い切ったあと、次の行に
（ ）で理由・前提・自虐・脱線を置く。

```
エラー時も `finally` でローディング解除しておいた方がいいかもです
（今だと失敗したときにスピナーが回りっぱなしになりそう）
```

## ルール 8: 構成

### インラインコメント

- 散文は 1〜3 行が基本（実績の中央値は 2 行・約 60 字）。1 行目に結論（提案か質問）、
  2 行目以降に理由を書く
- 概念の説明や、理由・条件を 3 つ以上並べるときは長くなってよい。並べる部分は
  箇条書き（`-`）にし、段落の間は空行で区切る。番号付きリストは使わない
- そのまま置き換えられる修正は ```` ```suggestion ```` で出す。説明用のコードは
  言語付きのコードブロック、差分は ```` ```diff ```` を使う
- 根拠は公式ドキュメント（MDN など）や解説記事の URL を単独の行に貼る。
  **URL は実際に開いて、該当する記述があることを確かめたものだけ貼る**
- 同じ指摘の 2 箇所目以降は「ここも」「こっちもそう」「ここも同上」だけにする
- 該当箇所が多いときは 1 箇所だけに書き、「（何箇所かありますがここだけコメントで）」と添える

### レビュー本文

- 指摘がなければ「LGTM!」だけにする（Approve の約 6 割がこれ）
- Approve に指摘や感想を添えるときも 1 行目は「LGTM!」にし、2 行目以降に
  1〜2 行添える（本文付き Approve の約 8 割がこの形）
  - 「細かいとこだけ書いときました！」
  - 「細かいこと書きましたがそれ以外はOKです！」
  - 「気になったとこだけコメントしときました！」
- 本筋とは別に気になる点があるときは、範囲を限って LGTM を出す
  （「修正内容自体はLGTM!」「〜についてはLGTMです！」）
- 感想や学びを一言添えることが多い（「〜面白いっすね」「〜初めて知りました」）
- 確かめきれない部分は正直に書く（「要件よくわかってないですが、〜は問題なさそうなので」）
- 条件付きで通すときは「〜だけ対応していただいたら、一旦マージしちゃっていいと思います！」
- Comment は本文なしでインラインだけ付けることが多い。本文を書くなら、何を見てほしいかを
  1〜2 行で書く。良い点を書くなら具体的に書き、無ければ書かない
- 見出しと太字は使わない（実績 633 件で見出し 0・太字 1）

### 返信

- 相手の発言の一部に答えるときは `> 引用` で該当部分だけ引いてから返す。会話欄はどの発言への
  返信かが見えないので、引用を付ける。ドキュメントの一文を引くときも `>` を使う
- 同意は「確かに！」「なるほどっす」「そっすね」「OKです！」「いいと思います！👍」
- 相手の説明で納得したら「なるほどです。それなら今のままで良さそうですね」
- 自分が間違っていたら、すぐ認めて軽く謝る（「私が知らなかっただけです…🙇」「あ、気のせいかも」）
- 調べて分かったことは URL と 1〜2 行の要約で返す

## ルール 9: 褒め方

- どこが良いかを具体的に言う（「関数の切り方わかりやすくていいですね👍」）
- お礼はカジュアルにする（「あざっす！」「あざます！」「ありがとうございます！」）
- 冒頭の定型的な褒め言葉（「素晴らしい PR ですね！」）や過剰な称賛はしない

## ルール 10: 自分の PR で作者として書くとき

ルール 3・5・6・7（確度・文末・語彙・記号）は返信にはそのまま使う。自分から付ける補足だけは
「！」が少なく（行末の 8%）、迷いの独り言は常体でよい（下記）。
作者側は次の点がレビュアー側と違う。

### 指摘に対応したとき

- **完了報告と SHA は push 済みの変更についてだけ書く。** push 前に「修正しました！」と書かない
- **対応しただけなら 1 行の完了報告で返す。** 返信の約 4 分の 1 がこれだけである
  - 「修正しました！」「消しました！」「追加しました！」「直しときました！」
  - 何をしたかが一言で言えるなら添える（「`ArgumentException` に統一しました！」）
- 納得して直したときは「確かに！　直しときました！」
- 一度は理由を説明し、そのうえで受け入れるときは「…が、確かに今回は〜の方がいいと思い直しました！」
- 複数の指摘をまとめて返すときや、対応箇所が分かりにくいときは SHA かリンクを示す。
  まとめて返すときは `> 引用` → 「DONE」→ リンクを指摘ごとに並べる
- 質問に肯定で答えるときは「です！」「ですです」「その通りです！」
- お礼は短くカジュアルにする（「あざます！」「ありがとうございます！！！🙇」）。
  「ご指摘ありがとうございます」から書き出さない
- 自分の見落としは素直に認める（「見落としてたみたいで…🙇」「確認不足ですみません！」）。
  短い感嘆（「OH…」）もまれに出る

### 異論があるとき

- 先に理由を書く。リスクや運用など具体的に書き、決めつけない
  （「それもありだと思うんですが、〜だと検知が遅れるのが怖いなと思いました」）
- 代替案で折り合うときは、何をしたかまで書く（「なので〜するようにしてみました」）
- 好みの問題なら引く（「この辺は好みの問題っぽいところあるので多数派に合わせます！」）
- 今は対応しないときは扱いを書く（「変更コスト大きいので一旦様子見で、意見聞いて考えます」「Issue にするかも」）

### 自分から付ける補足

- レビュアーに読んでほしい箇所には、意図を「です・ます」で書く
  （「ここが今回の処理本体です」「〜するために〜しています」）
- 迷っている点は独り言の形でそのまま開示する。補足の行の約 3 割は常体の独り言や
  言いさしで終わる（「〜か悩み」「これであってるんだろうか…」）。確かめていないときは
  そう書く（「とりあえず書いてみたけど動く保証はない」）。確かめたならルール 3 のとおり言い切る
- レビューを頼むときは「ツッコミお待ちしております…」「コメントいただければとー」
- 自分でマージするときは、理由を添えて告知する（「他で必要になったのでマージしちゃいます！」）。
  告知の投稿はマージの承認と一緒に確認を取る。マージが承認されていなければ告知も投稿しない
- 後で見返すための記録は「メモ：」で始める

## 書いた後の確認

1 つでも当てはまれば直す。

- 見出し・太字・番号付きリストを使っている
- `nit:` などのラベルを付けている
- 説明や列挙でもないのに、インラインの散文がコード・引用・URL を除いて 4 行以上ある
- 指摘の前に挨拶や全体の要約を置いている（具体的な良い点の一言は除く）
- 行末がほとんど「。」で終わっている
