# 概要

ブランチの位置を動かす操作の手順をまとめる。共通ルール（非対話時の終端、
命名規約、破壊的操作の承認、`<base-ref>` の定義）は `git-workflow` skill にある。

このファイルにあるルールは 3 と 7 である。ほかの番号は `git-workflow` の振り分け表で
持ち主を引く。

## ルール 3: ベースブランチの判定ロジック

新しい作業ブランチを切る手順は **3 ステップ** で行う: **(a) 選定 → (b) 取得・更新 → (c) 派生**。
途中を省略しない。

### (a) ベース選定

**上から順に評価し、最初にマッチした項を採用する。**

**以降 `master` / `main` と併記した箇所は、両方存在するなら常に `main` を優先する。**

1. **これから切るのが `hotfix/*` の場合** → **`master` / `main` から切る**
   - `develop` があっても hotfix では develop を使わない。ここで確定し、2 以降は見ない
   - 本番への緊急修正であるため、安定版からの派生が必要
2. **`hotfix/*` 以外で**、`git show-ref --verify --quiet refs/heads/develop` が成功する、
   または `git ls-remote --exit-code --heads origin develop` が成功する場合
   → **`develop` から切る**
3. それ以外は `master` または `main` を使用する
   - `main` と `master` の両方が存在する場合は `main` を優先
   - どちらも存在しない場合は `AskUserQuestion` で確認

hotfix の判定を先頭に置いてあるのは、develop の存在確認を先に評価すると
そこでマッチしてしまい、hotfix の例外に到達しないためである。

判定は **ローカルとリモートの両方** を確認する。
ローカルに develop がなくてもリモートに存在すればそれを優先する。

`develop` 以外を選ぶときも同じコマンドで存在を確認する。決め打ちしない。

```bash
git show-ref --verify --quiet refs/heads/<候補>
git ls-remote --exit-code --heads origin <候補>
```

### (b) ベースの取得・更新（派生直前に実施）

選定したベースは **派生直前にリモート最新へ追従させる**。古い HEAD から切ると競合・rebase 苦労の原因になる。

#### 通常ケース（作業ツリーが clean）

```bash
# `<base-ref>` が `<base>` の場合（ローカルにあり、ほかの worktree に無い）: 一旦 checkout してから rebase pull
git switch <base>
git pull --rebase origin <base>

# `<base-ref>` が `origin/<base>` の場合（リモートにしか無い、またはほかの worktree にある）: fetch して直接派生に使う
git fetch origin
```

後者は `refs/remotes/origin/<base>` を用意するための手順である。
(c)(d) がこの ref を参照するので、ここを飛ばすと `unknown revision` になる。
`git fetch origin <base>` のようにブランチを指定すると remote-tracking ref が
更新されるかが refspec 設定に依存するため、**引数なしの `git fetch origin` を使う**。

なお `git pull --rebase` はこの手順が明示的に指示する呼び出しであり、
git-workflow のルール 6 の要承認操作には**当たらない**（本文が規定する手順として実行してよい）。

#### 例外 1: 作業ツリーに未コミット変更がある場合

まず **ルール 7** の表で現在のブランチ種別に応じた選択肢を決め、`AskUserQuestion` で
ユーザーに選ばせる。選択肢ごとに (b) → (c) の続きが分岐する:

- **「コミットしてから進める」を選んだ場合** → `git-commit` スキルで現ブランチにコミット後、通常ケースに復帰
- **「stash して進める」を選んだ場合**:

  ```bash
  git stash push -u -m "<元のブランチ>: <退避した変更の内容>"
  # ここで通常ケースの (b) を実施する（<base-ref> で分岐。ここには再掲しない）
  git switch -c <new-branch> <base-ref> --no-track   # (c) 派生。ベースを明示する
  ```

  この場合は (b) 取得・更新を **完遂** する。この後 **(d) の検証を必ず実施する**。

  **`git stash pop` するかどうかは、退避した変更を新ブランチで使うかで決める。**
  無条件に pop しない。

  | 退避した変更は | pop するか |
  | --- | --- |
  | これから切るブランチで**続けて使う**もの | `git stash pop` する |
  | **別件**で、新ブランチに持ち込みたくないもの | **pop しない。** stash に残したまま作業を終える |

  混入を避けるために stash を選んだのに pop すると、1 コマンド後に持ち込む
  ことになる。**何のために退避したのかを思い出してから pop すること。**

  別件の stash は、自分で元のブランチへ戻って pop しない。戻ると、ユーザーが
  頼んだ新しいブランチにいない状態で作業を終えることになる。代わりに最終応答で、
  退避したときのメッセージと、戻し方（`git switch <元のブランチ>` →
  `git stash list` でメッセージから番号を探す → `git stash pop stash@{N}`）を伝える。
  番号は後から stash が積まれるとずれるので、番号だけで伝えない。
  stash の `drop` / `clear` は git-workflow のルール 6 の要承認操作なので、放置は安全側である。

- **「そのまま持ち込む」を選んだ場合**:

  ```bash
  git fetch origin                                   # <base-ref> が origin/<base> の場合のみ
  git switch -c <new-branch> <base-ref> --no-track   # (c) 派生。この経路でもベースを明示する
  ```

  git が派生を受け付ければ、未コミット変更（ステージ済み・未追跡を含む）は新ブランチへ
  そのまま移る。現在のブランチのコミットは引き連れない。この後 **(d) の検証を必ず実施する**。

  (b) のうち `git switch <base>` と `git pull --rebase` は **意図的にスキップ** する。
  `git pull --rebase` は既定の設定だと、未コミット変更があると実行を拒否するためである。
  `git fetch origin` は作業ツリーに触れないのでスキップしない。
  `<base-ref>` が `<base>` なら、更新しないまま派生元になる。追従させるなら、新ブランチで
  コミットした後に通常ケースの (b) で `<base>` を更新してから `git rebase <base-ref>` する
  （git-workflow のルール 8。rebase はルール 6 の要承認操作）。

  **変更のあるファイルの中身が現在の HEAD と `<base-ref>` で違うと、git は派生を拒否する**
  （`Your local changes to the following files would be overwritten by checkout` か
  `The following untracked working tree files would be overwritten by checkout`、exit 1）。
  このときブランチは作られず、現在のブランチも作業ツリーも変わらない。続けて (d) の
  `git log` を打つと、現在のブランチがベースの祖先なら空になり（成功に見える）、そうでなければ
  現在のブランチのコミットが並ぶ（混入に見える）。どちらも切り替わっていないだけなので、
  **(d) より先に `git branch --show-current` が `<new-branch>` かを確かめる。** 違えば git-recovery には入らない。

  拒否されたら `git switch -m` で押し通さない。`-m` は衝突しても exit 0 で新ブランチへ
  切り替わり、衝突マーカー入りの作業ツリーが残る。元の変更の控えが stash に残るかも
  git のバージョンで変わる（2.54 では残らず、2.56 では残った）。ルール 7 に戻って選び直す。

#### 例外 2: オフライン等で fetch / pull が失敗する場合

`AskUserQuestion` で「ローカル HEAD のまま切るか中断するか」を確認する。
「ローカル HEAD のまま切る」を選んだ場合は (b) をスキップして (c) へ。

**非対話時は「ローカル HEAD のまま切る」を採用**し、ベースが古いままである旨を
最終応答に明示する（作業を止めない）。

例外 1（未コミット変更がある場合）の非対話時の既定は **ルール 7 の表と「表の例外」** を見る。
ここには書かない。

### (c) 派生

更新済みのベースから新ブランチを切る。

**ベースを明示的に指定すること。引数なしの `git switch -c <new-branch>` は使わない。**
引数を省略すると現在の HEAD から切られるため、直前の作業ブランチ上にいた場合に
そのブランチのコミットを引き連れてしまう。

```bash
git switch -c <new-branch> <base-ref> --no-track
```

`<base-ref>` は git-workflow の `<base-ref>` 定義表で決めた参照（`<base>` または `origin/<base>`）。

`--no-track` を付ける。`<base-ref>` が `origin/<base>` だと、付けなければ新ブランチの
upstream が `origin/<base>` になる。git-push skill は upstream があると初回 push に `-u` を
付けず、`@{upstream}..HEAD` が push 済みのコミットも数え続ける。

### (d) 検証（省略不可）

**ブランチの位置が変わった直後は必ず、余計なコミットを引き連れていないことを
確認する。**

```bash
git log --oneline <base-ref>..HEAD
```

**出力が空であること**を確認する。
空でなければ**混入している**。git-recovery のルール 10 の復旧手順に従う。

#### いつ実施するか

「派生直後」だけではない。**HEAD が動く操作の後はすべて**が対象である。

| 操作 | (d) が要るか |
| --- | --- |
| `git switch -c` / `checkout -b`（派生） | **要る** |
| `git switch <既存ブランチ>`（切り替え） | **要る** |
| `git switch --detach <ref>` | **要る** |
| `git switch -C`（切り直し） | **要る** |
| `git stash pop` の後 | **要る**（作業ツリーが変わる） |
| `git rebase` の後 | **要る** |

直前の操作によって、確かめる相手が変わる。統合ブランチでは `<base-ref>..HEAD` が
必ず空になるので、確かめにならない。

| 直前の操作 | 確かめること |
| --- | --- |
| 新しいブランチを切った | `git branch --show-current` が新しいブランチであることと、`git log --oneline <base-ref>..HEAD` が空であること |
| 同じブランチの上で rebase / stash pop をした | `git log --oneline <base-ref>..HEAD` がそのブランチの作業だけであること |
| 統合ブランチへ切り替えた（pull の前後） | `git status -sb` の 1 行目のブランチ名が切り替え先で、`[ahead N]` が無いこと（統合ブランチに自分のコミットは無いはず） |
| `origin/<base>` に detach した | `git branch --show-current` の出力が空で、`git rev-parse HEAD origin/<base>` の 2 行が同じであること |
| 別の作業ブランチへ切り替えた | `git branch --show-current` が切り替え先であることと、`git log --oneline @{upstream}..HEAD` が push 前の自分のコミットだけであること（upstream が無ければ `<base-ref>..HEAD`） |

切り替えでも要るのは、**直前のコマンドが失敗していても気づけない**ため。
たとえば未コミット変更があると `git switch <base>` は失敗するが、続けて
`git switch -c <new> <base>` を流すとそちらは成功し、意図しないベースの
ブランチができる。作業ツリーには前のブランチの成果物が残ったままになる。

**実際の事故（2026-08-08）**: まさにこの経路で、別ブランチのコミットを含む
はずのない新ブランチに、そのブランチにしか無い成果物が乗った混在状態が
できた。`git status` を見て初めて気づいた。(d) を踏んでいれば即座に分かった。

この検証が要るのは、(a)〜(c) を守ったつもりで抜けても、
**そのままでは気づけない**ため。ブランチ名も差分も正しく見えてしまう。

実際の事故: 直前の作業ブランチ上にいることを意識しないまま
`git switch -c` を実行し、無関係なコミットを含んだ PR を作成した。
説明文には新しい変更のことしか書かなかったため、
**レビューされないまま別の変更がマージされた**（2026-08-07）。

## ルール 7: 未コミット変更の扱い

ブランチ切り替え・pull・ベース更新の前には必ず作業ツリーの状態を確認する。

```bash
git status --porcelain --untracked-files=normal
```

出力が空なら未コミット変更は無い。`--short` で判定しないのは、設定によって clean でも
`## <branch>` の行を出し、未追跡のファイルを出さないことがあるためである（git-push skill の Step 1 の 1.）。

未コミット変更がある状態でブランチ切り替えや pull を行おうとする場合、
`AskUserQuestion` で選択させる。選択肢は最大で以下の 3 つだが、
**実際に提示する数はブランチ種別と場面で変わる。下の表と「表の例外」が正本である。**

- 現在のブランチでコミットしてから進める（→ `git-commit` スキル）
- stash して進める
- そのまま持ち込む

### 選択肢と既定（この節が正本。他の節に既定を書かない）

| 現在のブランチ | 提示する選択肢 | 対話時の推奨 | 非対話時の既定 |
| --- | --- | --- | --- |
| 統合ブランチ（`develop` / `master` / `main`）、または detach した HEAD | stash / そのまま持ち込む の **2 択** | そのまま持ち込む | **そのまま持ち込む** |
| 作業ブランチ（`feature/*` / `hotfix/*`） | 3 択すべて | コミットしてから進める | **stash して進める** |

統合ブランチと detach した HEAD では「現在のブランチでコミットしてから進める」は
**git-workflow のルール 2 違反になるため提示しない**。そこにはコミットしないので、そこにある
未コミット変更は新ブランチの作業に属するとみなす。残る 2 択のうち「そのまま持ち込む」が
最短経路である。

作業ブランチ上の未コミット変更は、逆にそのブランチの作業の続きであることが多い。
持ち込むと新ブランチに別件の変更が混ざるため、非対話では stash を既定にし、
新ブランチで使うかは pop の時点で決める（ルール 3 (b) 例外 1）。

#### 表の例外

「そのまま持ち込む」を git が拒否したとき（ルール 3 (b) 例外 1）は、その選択肢を
除いて選び直す。作業ブランチでは残りの 2 択を提示し直し、統合ブランチでは stash しか
残らないのでそれで進める。非対話時はどちらのブランチでも stash して進める。
拒否されたファイルは HEAD とベースで中身が違うので、新ブランチで pop すると衝突しうる
（衝突しても stash は残る）。衝突したら git-recovery のルール 10 に従う。

git-pr のルール 11 のマージ直後の追従では「そのまま持ち込む」を提示しない。`<base-ref>` が
`<base>` なら、追従は `git pull --rebase` そのものが目的である。既定の設定の
`git pull --rebase` は、ステージ済みか未ステージの変更があると exit 128 で拒否する
（ルール 3 (b) 例外 1 は pull を飛ばして派生するので持ち込める）。`<base-ref>` が
`origin/<base>` なら追従は `git switch --detach` で、git は変更を持ち込める。ただ、マージ済みの
作業ブランチにある変更は、持ち込むと次に切るブランチへそのまま移る。この場面では、
作業ブランチならコミットと stash の 2 択で、推奨は stash である（マージ済みのブランチに
コミットしても、その PR には入らない）。統合ブランチと detach した HEAD、セッションの開始時に
作られたブランチ（デスクトップアプリの `claude/<名前>` など）では確認せずに stash して進める。
開始時のブランチにコミットすると、その PR に入らないうえ、追従の後の一括削除でも消えなくなる。
非対話時はどれでも stash して進める。未追跡ファイルだけなら pull は通るが、
場合分けを増やさないよう区別しない。

git-pr のルール 11 のマージの前に踏む場合は、コミットも持ち込みも提示しない（理由は
git-pr のルール 11 の「`gh pr merge` を打つ前」）。対話時は「stash してマージする」と
「マージを止める」の 2 択で、推奨は stash してマージする。変更を PR に入れたいなら、
ユーザーはマージを止めて PR を更新できる。非対話時は stash してマージする。

### 「安全な場合のみ」の判定

「そのまま持ち込む」もベースを明示して切るので、現在のブランチのコミットは
引き連れない。持ち込むのは未コミット変更だけであり、安全なのは
**その変更が新ブランチの作業に属する場合**である。

作業ブランチ上でこの選択肢を勧める前と実行する前に、`git status --short` と `git diff HEAD` で
中身が新ブランチの作業かを確かめる。git が派生を受け付けても、変更が現在の
ブランチのコミット（そこで足した関数など）に依存していれば新ブランチでは動かない。

      （引数を省くと現在の HEAD から切られ、直前の作業ブランチのコミットを引き連れる。
      `--no-track` が無いと、`origin/<base>` から切ったときに upstream が `origin/<base>` になる）
- [ ] **派生直後に** `git branch --show-current` が新しいブランチで、
      `git log --oneline <base-ref>..HEAD` が**空である**ことを確認したか？
      （※空を期待してよいのは**派生直後だけ**。作業が進んだブランチでは
      空でないのが正常で、そこで空を期待すると誤検知する）

      （直前のコマンドが失敗していても、次が成功して混在状態になることがある。
      統合ブランチへ切り替えた後は `git status -sb`、detach した後は `git rev-parse` で見る）
- [ ] 未コミット変更の扱いは明確か？
