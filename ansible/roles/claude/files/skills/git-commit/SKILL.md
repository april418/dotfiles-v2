# 概要

- このスキルはコミットの作成のみを行う。push は一切行わない。
- リモートブランチへの反映はユーザーが別途実施する。

**現在の状態:**

```bash
git status --short
```

**staged の変更:**

```bash
git diff --cached
```

**unstaged の変更:**

```bash
git diff
```

**直近のコミット履歴:**

```bash
git log --oneline -10
```

## 基本思想

**Revert 可能性を最優先**
各コミットは、他の機能を壊すことなく単独で revert できなければならない。
大きなまとめコミットよりも、小さく粒度の細かいコミットを優先する。
ファイル単位ではなく、ファイル内の hunk 単位での分割も検討する。

## ワークフロー

### Step 1: コミット対象外ファイルの確認

untracked ファイルに `.env`、credentials、`node_modules`、一時ファイル、
自動生成ファイルなど、コミットすべきでないものが含まれている場合のみ
`AskUserQuestion` でユーザーに確認する。
明らかにコミット対象のみの場合はこのステップをスキップする。

既に staged な変更がある場合は、ユーザーの意図を尊重する。
「この staged 状態のままコミットしますか？」と確認する。

### Step 2: 変更の分析とコミット設計

1. コミット履歴を確認し、既存のメッセージ構造・scope 命名規則を把握する
   - **見る履歴は HEAD から辿れるコミットだけ**（ベースの履歴を含む）。`--all` で
     ほかのブランチは見ない。マージされていないブランチの scope はまだ規約になっていない
   - scope は 2. でコミットの単位を決めた後、**コミットごとに、そのコミットに入れる
     パスで**次の表を上から順に見て決める。**前例の scope が今回の変更対象を
     指していなければ使わない**（前例が `login` だけで今回は README なら `login` は付けない）

     | 順  | 見るもの                                                              | 決め方                                                                                                                                                                                                                                                                               |
     | --- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
     | 1   | `git log --no-merges -n 20 --format=%s -- <そのコミットに入れるパス>` | そのパスに付いてきた scope のうち、今回の変更対象を指しているものを使う。複数あれば、パスに含まれるいずれかのディレクトリ名、またはファイル名（拡張子なし。大文字小文字は区別しない）と一致するもの。一致が無ければ件数の多いもの、同数なら新しいもの。指しているものが無ければ 2 へ |
     | 2   | `git log --no-merges -n 30 --format=%s --name-only`                   | scope がパスのどの階層の名前かを読み、今回のパスの同じ階層の名前を付ける（前例が `ansible/roles/zsh/` に `zsh` なら、`ansible/roles/node/` には `node`）。今回のパスがその階層で複数にまたがるなら、この 30 件の中で同じ組み合わせにまたがる前例の scope を使う。無ければ 3 へ       |
     | 3   | 下のフォールバック                                                    | 1・2 で決まらないとき（階層が読めない、今回のパスにその階層が無い等）                                                                                                                                                                                                                |

   - **フォールバック**:
     - 単一ファイル変更: ファイル名から拡張子を除いたもの（`parser.py` → `parser`）
     - 単一モジュール変更: ディレクトリ名・モジュール名（`src/auth/login.ts` → `auth`）
     - 横断的変更: 機能領域名（`readme` / `config` / `deps` 等）
   - **HEAD から辿れるコミットが 2 件未満の場合は、表の 1・2 と品質チェックの「既存の命名規則と整合しているか」を skip** し、Conventional Commits 仕様とフォールバックのみに従う
2. 変更内容全体を俯瞰し、論理的な単位に分解する
3. 各 hunk を個別に検討し、独立して revert 可能かを判断する

**コミット計画をユーザーに提示する。**
`AskUserQuestion` で「以下の単位でコミットします」と計画を示し、
承認を得てから Step 3 に進む。
意図しない分割でコミットされると revert が面倒になるため、必ず確認する。

ただし以下のいずれかに該当する場合は承認を省略してよい（Step 1 のスキップ条件と対称）:

- **単一論理単位の自明な変更**: 単一ファイルかつ単一の論理単位で、分割の余地がそもそも無い場合
- **明確に独立した分割**: 各ファイル/各 hunk が異なる種別の変更（例: 機能追加 + 無関係な docs 修正）で、分割粒度に複数解釈の余地が無い場合
- **ユーザーが事前指示済み**: 直近のユーザー指示で具体的なコミット計画（コミット数 / 分割単位 / メッセージ要旨）が既に明示されている場合

省略した場合は、最終応答（または `Discretionary fill-ins` 相当の箇所）に
「どの判断で承認を省略したか」を 1 行で明記する。

### Step 2.5: 整形と型チェックを最後に流す（コマンドがあれば省略不可）

**コミットの直前に、プロジェクトの整形コマンドを実行する。**

```bash
# 下の表の 1・2 で決まる例。プロジェクトに合わせる
pnpm run fix        # prettier / eslint --fix
cargo fmt
ruff format .
```

**整形コマンドは次の手がかりで、整形ツールごとに決める。** 対象のツールは 1〜3 の
どこかに出てくるものすべて（スクリプトなら、その中身で呼んでいるもの）。ツールごとに
上の行から見て、最初に当たった形で流す。`lint:fix` が eslint だけを呼び、CI が
`prettier --check` を流しているなら、eslint は 1、prettier は 2 で流す。

| 順  | 手がかり                                                                                             | 流すもの                                                                                                                                                                                                                                         |
| --- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | `package.json` の `format` / `fix` / `lint:fix`、`Makefile` / `Taskfile.yml` の `fmt` / `format`     | そのスクリプト・ターゲット                                                                                                                                                                                                                       |
| 2   | `.github/workflows/*.yml` の整形チェック                                                             | 書き込む形に直したもの（`prettier --check` → `prettier --write`、`shfmt --diff` → `shfmt --write`、`gofmt -l` → `gofmt -w`、`cargo fmt --check` → `cargo fmt`、`ruff format --check` → `ruff format`、`terraform fmt -check` → `terraform fmt`） |
| 3   | `.prettierrc*`、`pyproject.toml` の `[tool.ruff.format]` / `[tool.black]`、`.pre-commit-config.yaml` | そのツールを、コミットに入れるファイル（削除したものを除く）だけに流す（`prettier --write --ignore-unknown <files>` / `ruff format <files>` / `black <files>` / `pre-commit run --files <files>`）                                               |

2 でチェック用のフラグを外せば書き込む、と決めつけない。prettier・shfmt・gofmt は
フラグを外しただけだと、整形結果を標準出力に出すだけでファイルを書き換えず、exit 0 で
終わる。表に無いツールは、書き込む形を `--help` で確かめる。

2 のコマンドが `git ls-files` で対象を集めるなら、作業ツリーに無いパスを除いてから
渡す。削除を stage する前は、消したファイルも `git ls-files` に出る。shfmt はそのパスを
`lstat` のエラーにし、残りを書き換えたうえで exit 1 で終わるので、整形の失敗と見分け
にくい。`git rm --cached` で index から外す形にはしない。Step 3 でコミットを分けるとき、
先に stage した削除が最初のコミットに紛れ込む。

```bash
git ls-files -z -- '*.sh' | while IFS= read -r -d '' f; do [ -e "$f" ] && printf '%s\0' "$f"; done | xargs -0 shfmt --write
```

3 でリポジトリ全体に流さないのは、変更していないファイルまで書き換わって差分が
膨らむためである。prettier は扱えないファイルや存在しないファイルを渡すと exit 2 に
なるので、`--ignore-unknown` を付けて削除したものを除く。`pre-commit run` はフックが
ファイルを書き換えると exit 1 になる。もう一度流して exit 0 なら整形済みである。

**手がかりが 1 つも無い、または手がかりのツールが入っていなくて流せないときは、
`AskUserQuestion` で「整形せずにコミットする」か「整形コマンドを指定する」かを
確認する。** 設定の無い整形ツールを自分で選んで流さない。
Step 2 でコミット計画を確認するなら、同じ質問にまとめてよい。同じセッションの
同じリポジトリで一度答えを得たら、次のコミットからは聞き直さない。
非対話のときは流さずにコミットし、最終応答に整形していないことと理由（手がかりが
無い / ツールが入っていない）を 1 行書く。

**型チェックは整形の後に、git-push skill の Step 2 の型チェック（node.md と toolchains.md の表）と同じものを流す。**
条件はプロジェクトルートのファイルで見る。

| 種別                                                         | 条件                                                                             | 流すもの                                                     |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Node.js（`package.json` がある）                             | `scripts.typecheck` / `scripts.type-check` が定義されている                      | `<pm> run typecheck` / `<pm> run type-check`。両方あれば両方 |
| Python（`pyproject.toml` / `setup.py` / `setup.cfg` がある） | `mypy` が入っている（`.venv/bin/mypy` が実行可能か。無ければ `command -v mypy`） | `mypy .`。`.venv/bin` で見つけたら `.venv/bin/mypy .`        |

`<pm>` は git-push の node.md の「PM の決め方」（`packageManager` →
`devEngines.packageManager` → ロックファイル → `npm`）で決める。どの行にも当たらなければ
型チェックは流さず、聞かない。`tsconfig.json` などの設定ファイルから `tsc --noEmit` を
推測して流さない。プロジェクトが流していないコマンドの結果でコミットを止めることになり、
push 前のチェックとも食い違う。

**整形と型チェックを pnpm で流すとき（1 の `pnpm run <script>`、2・3 の `pnpm exec <tool>`、
型チェックの `pnpm run typecheck` / `pnpm run type-check`）は、`verifyDepsBeforeRun` の
指定のまま流す。環境変数の前置（`PNPM_CONFIG_VERIFY_DEPS_BEFORE_RUN=false`）や CLI フラグで
切らない**（package-manager skill のルール 1）。
pnpm 11 以降はこの設定の既定が `install` で、`pnpm run` と `pnpm exec` は `node_modules` が
ずれていれば install を流す。コミットの直前に `pnpm-lock.yaml` と `node_modules` を作ったり
書き換えたりし、store に無い依存は registry に取りに行く（`pnpm run fix`・`pnpm fix`・
`pnpm exec` のどれも 11.9.0 / 12.6.0 で実測）。dotfiles の pnpm ロールがグローバル設定で
`error` にしているので、ずれていれば `ERR_PNPM_VERIFY_DEPS_BEFORE_RUN` で止まり、何も
書き換えない。プロジェクトが pnpm-workspace.yaml で指定していればそれに従う。フックが
書き換えたものは、Step 3 の冒頭のとおりコミットの後に確かめる。

整形や型チェックが 0 以外で終わり、package.json の依存に宣言されたもの（ツール本体・
プラグイン・設定パッケージ）が見つからないと出力にあれば、`node_modules` が無いか
ロックファイルとずれていて、そのコマンドは流れていない。出力は次のような形になる。

- `command not found`、`: not found`（dash）、`Command "<tool>" not found`（`pnpm exec`）
- `Cannot find module '<pkg>'`、`Cannot find package '<pkg>'`
- `couldn't find the plugin`、`couldn't find the config`（ESLint）

型チェックの診断（tsc の `TS2307` など）は、見つからないものが package.json に宣言された
パッケージのときだけ当たる。mypy の `import-not-found`（`Cannot find implementation or library stub`）も、
見つからないモジュールが `pyproject.toml` などに宣言した依存の提供するものなら、同じく流れて
いないとみなす（`PyYAML` の `yaml` のように、配布名と import 名は違うことがある）。
相対パス・パスのエイリアス・宣言されていないパッケージの import はコードの誤りで、この段落にも
上の「手がかりのツールが入っていなくて流せないとき」にも当たらない。整形のツール本体と
そのプラグイン・設定パッケージが見つからず、package.json に宣言されていなければ、上の
「手がかりのツールが入っていなくて流せないとき」に従う。型チェックのものなら、下の
「流せなかった」に当たる。
出力に `ERR_PNPM_VERIFY_DEPS_BEFORE_RUN` か `Would you like to run "pnpm install"` が出たとき
（`error` / `prompt` の指定。10.33.0 の `prompt` はスクリプトを流さずに exit 0 で終わる）も、
そのコマンドは流れていない。
依存が見つからないときと pnpm が流さなかったときは、対話時は `AskUserQuestion` で出力の
該当行を添えて「依存を入れて（pnpm なら `pnpm install` を流して）から流し直す」か「流さずに
コミットする」かを聞く。
非対話時は流さずにコミットし、最終応答に流していないコマンドと出力の該当行を 1 行書く。
`verifyDepsBeforeRun` を切って流し直さない。
0 以外で終わったことだけでは、流れていないとみなさない。`eslint --fix` は、直せない指摘が
残ると書き換えたうえで 0 以外を返す。

**型チェックが 0 以外で終わり、上の依存の欠けにも pnpm が流さなかったときにも当たらなければ、
診断で分ける。**

- ファイルの位置（`<path>(<line>,<col>)` や `<path>:<line>`）を指す診断があれば、型エラーとして扱う。
  シェルのエラーの `(eval):1:` や `sh: 1:` は位置に数えない
- 位置を指す診断が 1 つも無ければ（PM が PATH に無い、`ERR_PNPM_UNSUPPORTED_ENGINE`、mypy の
  設定の誤りなど）、流せなかったとみなす。どのモードでも型チェックを流さずにコミットし、
  最終応答に流せなかったコマンドと出力の該当行を 1 行書く

型エラーは、対話時は `AskUserQuestion` で診断の該当行を添えて、「直してから流し直す」「型エラーを
残してコミットする」「コミットを中断する」を聞く。直したら整形から流し直す（下の順序のとおり）。
直したファイルを計画のどのコミットに入れるか（前からあった型エラーの修正なら別のコミット）を示し、
承認は Step 2 と同じ条件で取る。
非対話時は、計画のどれかのコミットに入れるファイルを指す診断があれば、計画のどのコミットも
作らず、最終応答にコミットしていないことと診断の該当行を書く。指す診断が無ければコミットし、
最終応答に型エラーが残っていることと該当行を書く。HEAD の時点で型エラーのあるリポジトリで、
非対話のコミットが毎回止まらないようにするためである。最終応答には、コミットに入れていない
ファイルの診断もこのコミットが原因でありうることを添える。型の食い違いは、定義を変えたファイル
だけでなく、それを使う側にも出る。出力に打ち切り（`pnpm -r` の `ERR_PNPM_RECURSIVE_RUN_FIRST_FAIL`
など）が出ていれば、出力に出ていないパッケージは調べていないことも添える。
診断のパスは流したディレクトリ（モノレポでは各パッケージのディレクトリ）から見たものである。
行の先頭にパッケージのディレクトリが付いていれば（`pnpm -r` の `packages/a typecheck: `）、それを
前に付けて比べる。turbo のようにパッケージ名が付くなら、その名前のパッケージのディレクトリを
前に付ける。どちらも付いていなければ、先頭に並ぶ `./` と `../` をすべて除いた診断のパスで、
コミットに入れるファイルのパスが終われば、指すとみなす。

型チェックの後（コミットの直前）に `git status --porcelain --untracked-files=normal` を流し、
コミット計画に無いロックファイル（`pnpm-lock.yaml` など）の行があれば、計画に足さずに
ユーザーに伝える。整形の前からあった変更かは区別しないが、Step 2 の確認で外すと決めた
ものは聞かない。対話時は `AskUserQuestion` で計画に足すか残すかを聞き、非対話時は残して
最終応答に書く。残すときは、次の git-push が Step 1 で止まることも添える。

整形を「作業の最初に一度やれば済むもの」として扱わない。**その後に 1 行でも
編集すれば、未整形の箇所が生まれる。** 手元では気づかず、CI の lint で落ちる。

順序を固定する。

```
編集 → 整形 → 型チェック → コミット
```

整形をコミット後に回すと、直すために追加のコミットが要り、履歴が汚れる。

**実際の失敗**: 整形を回した後にファイルを編集してコミットし、CI が
prettier で落ちた。同じ見落としを同一セッション中に 2 回繰り返した
（2026-08-08）。

### Step 3: コミットの実行

どの手順でも、`git commit` のたびに、その直前と直後に `git status --porcelain --untracked-files=normal`
を流す。直後の出力に、直前に無かったロックファイル（`pnpm-lock.yaml` など）の行か、そのコミットに
入れたロックファイルの行があれば、フックが書き換えたものとして伝える。ファイル単位の分割では、
直後の確認を `git stash pop` の前に済ませる。
pnpm 11 以降は、フックの中の `pnpm run` / `pnpm exec`（husky の `pnpm exec lint-staged` など）も
install を流す。install はロックファイルをステージしないので、書き換えはコミットに入らず
作業ツリーに残る（package.json をロックファイルより後に書き換えてコミットすると書き換わる。
11.9.0 / 12.6.0 で実測。10.33.0 は書き換えない）。
対話時は `AskUserQuestion` で「直前のコミットに足す」（`git add <ロックファイル>` の後に
`git commit --amend --no-edit`。コミットは作られているので、「pre-commit hook が失敗した場合」と
違って amend してよい）か「残す」かを聞く。非対話時は残して最終応答に書く。残すときは、
次の git-push が Step 1 で止まることも添える。足したロックファイルを計画の後のコミットに
入れる予定だったら、そのコミットから外す（ほかに入れるものが無ければ、そのコミットは作らない）。
ファイル単位の分割で、フックが書き換えたロックファイルのせいで `git stash pop` が `would be overwritten` で
止まったら、stash を残したまま止める。stash の場所と、作業ツリーのロックファイルはフックが
書き換えたものであることを伝える。ロックファイルを捨てて pop し直すかはユーザーが決める
（git-workflow のルール 6）。
フックが registry に届かないなど、手元で直せない理由で落ちたら（コミットは作られない）、
直そうとせずに止め、フックの出力の該当行を伝える。ファイル単位の分割で退避していれば、
`git stash pop` で戻してから止める。hunk 単位の分割なら手順 1 の stash を残し、巻き戻した hunk が
あることと stash の場所を伝える。環境変数の前置や `--no-verify` で通さない。

#### 基本: すべての変更を1コミット、またはファイル単位で1コミット

```bash
git add <file1> <file2>
git commit -m "$(cat <<'EOF'
<type>(<scope>): <要約>

<詳細>
EOF
)"
```

#### 複数コミットに分割する場合（ファイル単位）

変更を複数コミットに分けたいが、各コミットはファイル単位で分割できる場合。
`git stash --keep-index` で、まだコミットしない変更を退避する。

```bash
# 1つ目のコミット
git add <file1>
git stash --keep-index
git commit -m "$(cat <<'EOF'
<type>(<scope>): <要約>

<詳細>
EOF
)"
# pop の前に、Step 3 の冒頭のロックファイルの確認を済ませる
git stash pop

# 2つ目のコミット
git add <file2>
git commit -m "$(cat <<'EOF'
<type>(<scope>): <要約>

<詳細>
EOF
)"
```

#### 同一ファイル内を hunk 単位で分割する場合

対話的コマンド（`git add -p` / `git add --interactive`）は使用不可。
以下の手順で Edit ツールを使い、最後に検証する。

**前提条件:**

- 新規ファイル（untracked）は hunk 分割の対象外。必ずファイル単位でコミットする。
- 対象は tracked なテキストファイルのみ。binary / symlink は対象外。
- 開始時に clean index であること（staged 変更がない状態）。

**手順:**

```bash
# 1. 検証用スナップショットを保存（pop しない）
git stash
STASH_OID=$(git rev-parse stash@{0})
git stash apply
```

```bash
# 2. 1つ目のコミット用に、含めない hunk を Edit ツールで HEAD の内容へ巻き戻す
#    起点状態: `git stash apply` 直後は全 hunk が作業ツリーに乗っている。
#    操作: このコミットに含めたい hunk はそのまま残し、含めない hunk のみ
#    `git show HEAD:<file>` の対応箇所と一致するように Edit で書き戻す。
git add <file>
git commit -m "$(cat <<'EOF'
<type>(<scope>): <要約>

<詳細>
EOF
)"
```

```bash
# 3. 2つ目のコミット用に、巻き戻していた hunk を Edit ツールで再適用する
#    起点状態: 1 つ目のコミット後は HEAD に含めた hunk のみ反映済みの状態。
#    操作: 残りの hunk を Edit で適用する（stash 内容が既知なので参照しながら）。
git add <file>
git commit -m "$(cat <<'EOF'
<type>(<scope>): <要約>

<詳細>
EOF
)"
```

```bash
# 4. 全コミット完了後、検証
git diff $STASH_OID HEAD
# → 空なら変更漏れなし。差分が出たら漏れまたは余計な変更がある。
# 計画に入れずに残したファイル（Step 2.5 のロックファイルなど）や、フックが書き換えて
# amend で足したファイル（Step 3 の冒頭）があれば、それを除いて見る。
# パスごとに ':(top,exclude)<パス>' を並べる。<パス> は git status --porcelain が出した
# リポジトリルートからのパス:
# git diff $STASH_OID HEAD -- ':(top,exclude)<パス 1>' ':(top,exclude)<パス 2>'
```

```bash
# 5. 検証 OK なら stash を破棄
git stash drop
```

**検証が失敗した場合（diff が空でない場合）:**
作業を中断し、`AskUserQuestion` でユーザーに状況を報告する。
勝手に修正を試みない。

## コミットメッセージ形式

```
<type>(<scope>): <日本語の一行要約>

<日本語の詳細説明>
```

### type（英語のまま）

`feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`

#### 曖昧になりやすい典型ケースの指針

複数の type に当てはまりそうな変更でブレないように、以下を優先採用する。

| ケース                                            | 採用 type                                       | 理由                                                                                                                                     |
| ------------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 型ヒント・型注釈の追加（挙動不変）                | `refactor`                                      | 公開シグネチャの契約変更で、後で `refactor` でも `feat` でも grep されうるが、振る舞い不変なら `refactor` に寄せて履歴の意味を一貫させる |
| f-string 化・文字列結合の書き換え（挙動不変）     | `refactor`                                      | 可読性目的のコード書き換え。`style` はフォーマッタ任せの空白/改行調整に限定                                                              |
| import 並び替え・空白/改行調整のみ                | `style`                                         | フォーマッタ準拠の見た目だけの変更                                                                                                       |
| 依存パッケージのバージョン更新                    | `chore`                                         | ビルド/リリース関連の運用作業。挙動差は `fix` / `feat` の範疇に入れず `chore(deps)`                                                      |
| 設定ファイル（lint / CI / editorconfig 等）の調整 | `chore` または `ci`                             | CI 設定は `ci`、それ以外の運用設定は `chore`                                                                                             |
| テストコードのみ追加・修正                        | `test`                                          | 本番コードを触らない場合                                                                                                                 |
| ドキュメント（README / コメント / CHANGELOG）のみ | `docs`                                          | 挙動に影響しない記述のみ                                                                                                                 |
| エラーメッセージ・例外メッセージの改善            | `fix` if 既存バグ起因、`refactor` if 可読性目的 | ユーザー体験影響の有無で振り分け                                                                                                         |

### 記載ルール

- type と scope は英語
- subject は日本語で簡潔に一行
- body は日本語で **なぜこの変更が必要だったか** を中心に書く
  - 変更の背景・経緯
  - この実装を選んだ理由・判断根拠
  - 変更ファイルの列挙は不要（diff で分かるため）
- 変更のきっかけ（レビューで指摘された、〜に言われた等）は書かない
  - 誰に言われたかはコードの文脈と無関係
  - 代わりに「〜という問題があった」など、技術的な課題として記述する
  - 例: NG「レビューで〜の指摘を受けた」→ OK「〜という問題があった」
- 変更の背景や意図が不明な場合は `AskUserQuestion` でユーザーに確認してから書く
  - **autonomous / 非対話モード時の例外**: 確認を取れない実行コンテキスト（subagent 実行、自動化スクリプト等）では、コードと diff から **合理的に推測できる動機** を body に記述してよい。その場合は最終応答（または Discretionary fill-ins 相当の箇所）に「推測で書いた」旨を 1 行で明記する
  - **推測の許容範囲**: 以下は OK
    - diff から自明に導けるユースケース（例: `normalize()` で空白を畳み込む → 「後続比較の安定化」）
    - API 設計判断（例: 既存関数の責務を保ったまま別関数化）
    - エラーハンドリングの意図（例: `ValueError` 送出 → 「呼び出し側で捕捉しやすくする」）
  - **推測すべきでないもの**: ビジネス背景の創作（例: 「営業からの要望」「特定顧客の要求」等の外部要因）。誰が・いつ・なぜ依頼したかは diff から導けないので書かない
- subject だけで変更理由が十分伝わる自明な変更（typo 修正、`.gitignore` への追加等）は body を省略してよい
- 1 行あたり 72 文字程度で改行する

## pre-commit hook が失敗した場合

- hook の失敗内容を確認し、問題を修正する。registry に届かないなど手元で直せない理由なら、
  Step 3 の冒頭のとおり止める
- 修正後は **新しいコミットを作る**（`--amend` は使わない）
  - hook 失敗時はコミットが作成されていないため、`--amend` すると直前の無関係なコミットを書き換えてしまう
- 修正内容が元の変更と論理的に同じなら、1つのコミットにまとめてよい

## 品質チェック

- **最後の編集の後に整形コマンドと型チェックを流したか**（Step 2.5。整形コマンドが無ければ、ユーザーに確認したか。非対話なら、流していないことを最終応答に書いたか。型チェックは表の行に当たらなければ流さない。型エラーが出たら、対話時は聞いたか。非対話時は、計画のどれかのコミットに入れるファイルを指す診断があればコミットしていないか）
- **`git commit` の直前と直後の `git status` で、フックが書き換えたロックファイルを確かめたか**（Step 3）
- このコミットは単独で revert 可能か
- 最小の論理単位になっているか
- 変更の背景・意図が body に明確に書かれているか（自明な変更を除く）
- 既存の命名規則と整合しているか

## メッセージの例

```
fix(auth): トークン検証時に例外が適切に処理されない問題を修正

期限切れトークンが送信された場合に 500 エラーが発生していた。
例外処理を追加し、401 を返却するよう修正した。
既存の認証ロジックへの影響はない。
```

```
refactor(search): 検索処理をサービス層へ分離

コントローラに集中していた検索ロジックを SearchService に移動した。
責務を明確化し、テスト容易性を向上させる目的。
挙動自体の変更はない。
```

```
docs(readme): typo を修正
```
