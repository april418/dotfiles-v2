# orchestrate

引数: $ARGUMENTS

ふだんの委譲の条件と指示文の要件は、グローバル指示の「サブエージェント」節にある。この skill はその上に、
複数のトラックを台帳で並行して回す手順を足す。Issue の読み書きは gh-issue skill が、ブランチ・コミット・PR は
git-workflow skill の振り分け表にある skill が持つ。どれも、その操作の前に Skill ツールで呼ぶ。

この skill はユーザーだけが呼べるので、会話の要約の後に本文が戻らなくても、モデルは呼び直せない。台帳の節の
1 行目に `${CLAUDE_SKILL_DIR}/SKILL.md` を書き、要約の後は台帳とこのファイルを Read で読み直してから続ける。
gh-issue と `git-*` の skill は、要約の後に Skill ツールで呼び直す。

## 0. 引数で入口を分ける

| 引数                                       | 対象                                 | GitHub への書き込み                                                                         |
| ------------------------------------------ | ------------------------------------ | ------------------------------------------------------------------------------------------- |
| 無し                                       | 作業中のリポジトリのバックログ       | 2. で着手の確認を得た Issue にだけ書く                                                      |
| Issue の番号（`#12 #15`、`OWNER/REPO#12`） | 名指しした Issue                     | 同じく 2. で着手の確認を得た Issue にだけ書く                                               |
| 作業の説明                                 | 説明した作業。Issue には対応付けない | Issue には書かない。範囲の外で見つけた作業を Issue にするかは gh-issue の「Issue を立てる」 |

Issue の番号は対象の指定で、着手の確認にも PR の名指しにもならない（gh-issue の「書き込みと承認」）。引数に番号と
一緒に書き込みが書かれていれば（`#12 #15 着手の印を付けて PR まで`）、ユーザー自身の言葉による着手の確認と PR の
名指しとして扱い、書かれた書き込みだけを行う。名指しした Issue の `status` が `ready` でも `external` でもなければ、
gh-issue の「着手中か確かめる」の扱いに従い、着手せずにそう伝える。

非対話では、引数に書かれた書き込みのほかは確認を取れない。引数が無ければ、2. の仕分けと組の提案だけを最終応答に
書いて終える。番号だけを渡されたら、Issue には書かずに直し、git-workflow のルール 0 のとおり push まで進め、
書かなかったことを最終応答に書く。

## 1. 分けてよいかを先に決める

分割は単独で進める場合の数倍のトークンを使い、逐次の作業では精度も落ちる。次のどれかに当たるなら分割せず、
メインがそのまま進め、そう決めた理由を 1 行でユーザーに伝える。Issue の番号で呼ばれたときも同じで、分けない
ときもその Issue の着手・PR・閉じ方は gh-issue に従う。

- 作業の大半が、前の結果を見て次を決める編集とデバッグの連続である
- トラックどうしが同じファイルか、同じ未確定の設計判断に依存する
- 数十回のツール呼び出しで終わる

## 2. 組を決める

gh-issue skill を呼ぶ。引数が無ければ、その「読む」「着手中か確かめる」「仕分ける」に従ってバックログを仕分ける。
Issue の番号を渡されたら、その Issue を `view` で読む。引数に書き込みも書かれていれば、その範囲の着手の確認は
済んでいるので、問いは書かれていない書き込み（ブランチ名など）にだけ出す。

- 着手できる Issue から、同時に回す組を選ぶ。1 組のトラックが 3〜5 本に収まる量にし、触るファイルが重なる
  Issue は別の組に分けるか、1 トラックにまとめる
- `AskUserQuestion` の複数を選べる問いで組を確かめる。これが gh-issue の「書き込みと承認」の着手の確認になる。
  選択肢は Issue にし、説明に次を書く
  - トラックの切り方と、ブランチ名の案（git-workflow のルール 1。選ばれたらその名前で切る）
  - 閉じ方（`Closes` か `Refs` か、マージの後に閉じるか）
  - その Issue への書き込み: 着手の印とコメント、「#N の PR を作る」、`repo` の `missing_labels` にあれば「ラベルを作る」
  - public か internal のリポジトリなら、ラベルとコメントが読まれること
- 情報が足りない・大きすぎる・済んでいそうな Issue と `external` の Issue は、組とは別に、提案（質問のコメント、
  分け方、クローズ）として並べる。どれもそのつどの承認が要る
- 断られた Issue は、gh-issue の「提案から外す」に従う

## 3. 台帳を作る

グローバル指示の「判断ログ」のファイルに `## 台帳: <作業名>` の節を作る。会話の要約ではトラックの状態が落ちる
ので、このセッションの状態は台帳を正本にする。ほかのセッションと共有する状態（着手、節目）は Issue に置く。
判断ログのファイルに書けないとき（`~/.claude/` への書き込みを確認する窓口が無い非対話の実行など）は、作業ツリーの
直下の `.orchestrate-ledger.md` に同じ節を作る。`.git/` も `~/.claude/` と同じく保護されたパスで断られるので
使わない。dotfiles の git ロールがグローバルな ignore に `.orchestrate-*` を入れているので、このファイルは
`git status` に出ず、コミットにも stash にも入らない。

- 1 行目: この手順のパス（`${CLAUDE_SKILL_DIR}/SKILL.md`）と、要約の後に Read で読み直すこと
- 呼ばれたときの引数。Read で読み直したこのファイルでは引数が置き換わらず、入口（0.）が分からなくなる
- 目標と完了の条件。テストやコマンドで確かめられる形で書く
- 確認済みの事実、未確認の点、仮説（外れた仮説も消さずに残す）
- Issue の一覧: リポジトリと番号、閉じ方、ブランチ、PR、状態
- トラックの一覧: 名前、範囲（触るファイル）、依存、担当（自分か subagent の種類）、worktree のパス、状態、
  停滞の回数、対応する Issue

着手の確認を得た Issue には、トラックを出す前に gh-issue の「着手する」で印を付ける。

SessionStart フックは、判断ログのファイルが大きいと本文を載せずにパスだけを示す。判断ログのファイルは cwd ごとに
分かれるので、作業の間は `cd` せず、`git -C` と絶対パスを使う。

## 4. トラックに分ける

文脈の境界で切る。機能を作るトラックがそのテストも書き、調べる・実装する・テストする・レビューするの役割では
切らない。役割で切ると引き継ぎのたびに文脈が落ち、調整に作業より多くのトークンを使う。

- 依存があるトラックは直列にし、先のトラックの結果を次の指示文に書き込む
- 書き込むトラックどうしは触るファイルを重ねない。重なるなら 1 本にまとめる
- 1 つの Issue に独立した項目が複数あれば、トラックを分ける。同じファイルを触る小さい Issue どうしは 1 トラックに
  まとめ、1 つの PR で閉じてよい
- 組に Issue が複数あるとき、書き込むトラックは Issue ごとに worktree を分けるか、直列にする。PR は Issue ごとに
  分けるので、同じツリーで混ぜると、どの変更がどの Issue のものかを分けられない
- subagent の worktree（`isolation: worktree`）はリモートの既定ブランチから切られ、作業ブランチの未マージの
  コミット（`git log --oneline origin/<既定ブランチ>..HEAD`）を持たない。書き込むトラックを worktree に分けるのは、
  そのコミットが要らないときだけにし、要るなら同じツリーで触るファイルを分けるか、直列にする
- 同時に走らせるのは 3〜5 本までにし、残りは先のトラックが終わってから出す。同時実行の上限
  （`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`）はトラックの中で起こす subagent も数え、達すると待たずに断られ、
  エラーは再試行しないよう指示する。空きが出れば次の起動は通る

## 5. 委譲する

指示文には、グローバル指示の要件に加えて次を書く。

- このトラックの範囲と、触らない範囲
- 台帳の確認済みの事実と外れた仮説。書かないと、同じ調査を別の subagent が繰り返す
- git と GitHub への書き込み（add・commit・branch・stash、Issue のコメントとラベル、PR）をしないこと。どれも
  メインが行う。並列の subagent が git に書き込むと index のロックを取り合い、git-workflow を読んだ subagent は
  worktree のブランチを規則外とみなして別のブランチを切る。Issue に書くと、同じ Issue の書き手が増える
- Issue のあるトラックには、その Issue の `agent:doing` はこのセッションが付けた印であること。gh-issue の着手の手順は
  通らず、Issue には書かない。書かないと、subagent は gh-issue の「着手中か確かめる」に従って作業を断る
- worktree のトラックには、gitignore されたファイル（`node_modules`、`.env` など）が無いこと。依存を入れてから
  試すか、試せなかったことを報告に書く
- 返す形: 変えたファイルの一覧、流したテストとその結果、worktree のパス

## 6. 進み具合を見る

報告が届くたびに台帳を更新し、次を確かめる。

- 完了の主張に根拠（テストの結果、diff、コマンドと終了コード）が付いているか。付いていなければ完了にしない
- 同じ調査や同じ失敗を繰り返していないか
- 前進しているか。前進が無ければ停滞の回数を 1 増やし、2 回になったら計画を見直す（範囲を変える、自分で引き取る、
  ユーザーに聞く）

決めたこと、外れた仮説、手放すときの状態のような節目は、gh-issue の「コメントに残すもの」に従ってメインが Issue に
書く。報告のたびには書かない。

## 7. 合流する

合流はメインが 1 本ずつ行い、トラックごとにコミットする（git-commit skill）。

- Issue のあるトラックは、その Issue のブランチに合流する。ブランチは 2. で決めた名前で、git-branch skill の
  ルール 3 でベースから Issue ごとに切る。前の Issue のブランチから切ると、そのコミットを引き連れる。メインの checkout をほかの
  セッションが使っていれば、`git worktree add` でベースを指定して切る
- 同じツリーのトラックは、そのトラックの diff を読んでからコミットする
- worktree のトラックは、テストが通ったものだけを取り込む。`git -C <worktree> add -A` の後、
  `git -C <worktree> diff --cached --binary` をパッチに書き出し、作業ツリーで `git apply --3way <パッチ>` を
  当ててからコミットする。`git merge` は使わない（git-workflow のルール 8）。パッチは作業ツリーの外（scratchpad が
  あればそこ、無ければ `mktemp -d` で作ったディレクトリ）に書く。外なら、当てた後に取り除く手間が要らない。外に
  書けなければ作業ツリーの直下に `.orchestrate-<トラック名>.patch` として書き、当てた後に `evacuate` で取り除く。
  トラック名は英小文字・数字・`-` にする。空白や `/` が入ると、書き出しが別のパスを指して失敗する
- 合流のたびにテストを流し、壊れたらどの合流で壊れたかを特定してから次へ進む
- コンフリクトは git-recovery のルール 10 に従う

## 8. PR を出して次の組へ

- Issue ごとに git-pr skill で PR を出す。出すのは、着手の確認で「#N の PR を作る」を選ばれた Issue と、ユーザーが
  PR を名指しした作業だけにし、ほかは git-workflow のルール 0 のとおり push で止める。本文の Issue の参照は
  gh-issue の「閉じ方」に従う
- マージは PR ごとに git-pr skill のルール 11 の承認を得る。着手の確認はマージの承認にならない
- マージで閉じない Issue（`Refs` で参照した、閉じるキーワードが効かない base だった）は、マージの後に gh-issue の
  「手放す・済ませる」に従う
- 組が終わったら、gh-issue でバックログを読み直して 2. に戻る。ほかのセッションが立てた Issue もここで拾う。
  マージ待ちの PR が残っていても、触るファイルが重ならなければ次の組に進んでよい
- 止めるのは、着手できる Issue が無くなったとき、ユーザーが止めたとき、2 組続けて前進しなかったとき。非対話では
  名指しした Issue を終えたら止め、次の組には進まない

## 9. 終える

- フルのテストスイート（無ければビルドと lint）を流し、台帳の完了の条件と突き合わせる
- 指示文の改訂や複数ファイルにまたがる設計判断を含むなら、グローバル指示のとおり `implementation-validator` に
  見せる
- 終わらなかった Issue は、gh-issue の「手放す・済ませる」に従って印を外し、途中の状態をコメントに残す
- 台帳の節の見出しに「（完了）」を付け、トラックごとの結果を残す
- 最終応答に、Issue とトラックごとの結果（PR、閉じたか、印を外したか）、合流したもの・しなかったもの、未確認の点、
  残った worktree のパスを書く。worktree を消すか（`git worktree remove`）はユーザーが決める。作業ツリーの直下に
  `.orchestrate-*`（台帳、取り除けなかったパッチ）が残っていれば、そのパスも書く。ignore されて `git status` には
  出ないので、書かないと残っていることに気づけない

## 対象が 10 を超えるとき

同じ指示を多数の対象（ファイル、パッケージ、URL）に当てる作業で、対象が 10 を超えるなら Workflow ツールの
スクリプトで回してよい。トークンを大きく使うので、回す前に対象の数と見込みのエージェント数を示して
`AskUserQuestion` で確かめる。スクリプトを書く前に workflow-authoring skill を読む。
