# orchestrate

対象の作業: $ARGUMENTS

ふだんの委譲の条件と指示文の要件は、グローバル指示の「サブエージェント」節にある。
この skill はその上に、複数のトラックを台帳で並行して回す手順を足す。

## 1. 分けてよいかを先に決める

分割は単独で進める場合の数倍のトークンを使い、逐次の作業では精度も落ちる。次のどれかに
当たるなら分割せず、メインがそのまま進め、そう決めた理由を 1 行でユーザーに伝える。

- 作業の大半が、前の結果を見て次を決める編集とデバッグの連続である
- トラックどうしが同じファイルか、同じ未確定の設計判断に依存する
- 数十回のツール呼び出しで終わる

## 2. 台帳を作る

グローバル指示の「判断ログ」のファイルに `## 台帳: <作業名>` の節を作る。会話の要約では
トラックの状態が落ちるので、状態は台帳を正本にする。判断ログのファイルに書けないとき
（`~/.claude/` への書き込みを確認する窓口が無い非対話の実行など）は、作業ツリーの直下に
`.orchestrate-ledger.md` を未追跡のまま置き、コミットに入れない。

- 目標と完了の条件。テストやコマンドで確かめられる形で書く
- 確認済みの事実、未確認の点、仮説（外れた仮説も消さずに残す）
- トラックの一覧: 名前、範囲（触るファイル）、依存、担当（自分か subagent の種類）、
  worktree のパス、状態、停滞の回数

圧縮の後は、台帳を Read で読み直してから続ける。SessionStart フックは、ファイルが大きいと
本文を載せずにパスだけを示す。判断ログのファイルは cwd ごとに分かれるので、作業の間は
`cd` せず、`git -C` と絶対パスを使う。

## 3. トラックに分ける

文脈の境界で切る。機能を作るトラックがそのテストも書き、調べる・実装する・テストする・
レビューするの役割では切らない。役割で切ると引き継ぎのたびに文脈が落ち、調整に作業より
多くのトークンを使う。

- 依存があるトラックは直列にし、先のトラックの結果を次の指示文に書き込む
- 書き込むトラックどうしは触るファイルを重ねない。重なるなら 1 本にまとめる
- subagent の worktree（`isolation: worktree`）はリモートの既定ブランチから切られ、作業
  ブランチの未マージのコミット（`git log --oneline origin/<既定ブランチ>..HEAD`）を持たない。
  書き込むトラックを worktree に分けるのは、そのコミットが要らないときだけにし、要るなら
  同じツリーで触るファイルを分けるか、直列にする
- 同時に走らせるのは 3〜5 本までにし、残りは先のトラックが終わってから出す。同時実行の
  上限（`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`）はトラックの中で起こす subagent も数え、
  達すると起動を断られて再試行もできない

## 4. 委譲する

指示文には、グローバル指示の要件に加えて次を書く。

- このトラックの範囲と、触らない範囲
- 台帳の確認済みの事実と外れた仮説。書かないと、同じ調査を別の subagent が繰り返す
- git の書き込み（add・commit・branch・stash）をしないこと。コミットはメインが合流の
  ときに行う。並列の subagent が git に書き込むと index のロックを取り合い、git-workflow を
  読んだ subagent は worktree のブランチを規則外とみなして別のブランチを切る
- worktree のトラックには、gitignore されたファイル（`node_modules`、`.env` など）が無いこと。
  依存を入れてから試すか、試せなかったことを報告に書く
- 返す形: 変えたファイルの一覧、流したテストとその結果、worktree のパス

## 5. 進み具合を見る

報告が届くたびに台帳を更新し、次を確かめる。

- 完了の主張に根拠（テストの結果、diff、コマンドと終了コード）が付いているか。付いて
  いなければ完了にしない
- 同じ調査や同じ失敗を繰り返していないか
- 前進しているか。前進が無ければ停滞の回数を 1 増やし、2 回になったら計画を見直す
  （範囲を変える、自分で引き取る、ユーザーに聞く）

## 6. 合流する

合流はメインが 1 本ずつ行い、トラックごとにコミットする（git-commit skill）。

- 同じツリーのトラックは、そのトラックの diff を読んでからコミットする
- worktree のトラックは、テストが通ったものだけを取り込む。`git -C <worktree> add -A` の
  後、`git -C <worktree> diff --cached --binary` を作業ツリーの外（scratchpad があれば
  そこ、無ければ `$TMPDIR`）のパッチに書き出し、作業ツリーで `git apply --3way <パッチ>` を
  当ててからコミットする。作業ツリーに書くと、パッチが `git status` に出てコミットに紛れる。
  `git merge` は使わない（git-workflow のルール 8）
- 合流のたびにテストを流し、壊れたらどの合流で壊れたかを特定してから次へ進む
- コンフリクトは git-recovery のルール 10 に従う

## 7. 終える

- フルのテストスイート（無ければビルドと lint）を流し、台帳の完了の条件と突き合わせる
- 指示文の改訂や複数ファイルにまたがる設計判断を含むなら、グローバル指示のとおり
  `implementation-validator` に見せる
- 台帳の節の見出しに「（完了）」を付け、トラックごとの結果を残す
- 最終応答に、トラックごとの結果、合流したもの・しなかったもの、未確認の点、残った
  worktree のパスを書く。worktree を消すか（`git worktree remove`）はユーザーが決める

## 対象が 10 を超えるとき

同じ指示を多数の対象（ファイル、パッケージ、URL）に当てる作業で、対象が 10 を超えるなら
Workflow ツールのスクリプトで回してよい。トークンを大きく使うので、回す前に対象の数と
見込みのエージェント数を示して `AskUserQuestion` で確かめる。スクリプトを書く前に
workflow-authoring skill を読む。
