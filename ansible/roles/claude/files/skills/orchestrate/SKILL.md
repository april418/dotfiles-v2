# orchestrate

引数: $ARGUMENTS

ふだんの委譲の条件と指示文の要件は、グローバル指示の「サブエージェント」節にある。この skill はその上に、
複数のトラックを台帳で並行して回す手順を足す。Issue の読み書きは gh-issue skill が、ブランチ・コミット・PR は
git-workflow skill の振り分け表にある skill が持つ。どれも、その操作の前に Skill ツールで呼ぶ。

この skill はユーザーだけが呼べるので、会話の要約の後に本文が戻らなくても、モデルは呼び直せない。台帳の節の
1 行目に `${CLAUDE_SKILL_DIR}/SKILL.md` を書き、要約の後は台帳とこのファイルを Read で読み直してから続ける。
gh-issue と `git-*` の skill は、要約の後に Skill ツールで呼び直す。

## 0. 引数で対象を分ける

| 引数                                       | 対象                                                                  | GitHub への書き込み                                                                                                               |
| ------------------------------------------ | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 無し                                       | 作業中のリポジトリのバックログ                                        | 2. で着手の確認を得た Issue にだけ書く                                                                                            |
| Issue の番号（`#12 #15`、`OWNER/REPO#12`） | 名指しした Issue（計画の親なら、その開いた sub-issue）                | 引数か 2. で着手の確認を得た Issue にだけ書く                                                                                     |
| 作業の説明                                 | 説明した作業。2. で分解して計画を立て、親の Issue と sub-issue にする | 2. の計画の問いで承認を得た書き込み（Issue を立てる、既にある Issue をつなぐ、依存、閉じる）と、着手の確認を得た Issue にだけ書く |

どの行でも、2. の提案（質問のコメント、分け方、クローズ）、ほかのセッションの着手の済ませ忘れと、閉じ損ねを
済ませること、9. で計画の親を閉じること（このセッションの計画の問いで承認を得た親を除く）は、そのつど対象を
名指しした承認を得てから書く。自分の着手の済ませ忘れは、gh-issue の「着手中か確かめる」に従う。

Issue の番号は対象の指定で、着手の確認にも PR の名指しにもならない（gh-issue の「書き込みと承認」）。引数に番号と
一緒に着手の目印が書かれていれば（`#12 #15 ラベルが無ければ作って、着手の目印を付けて PR まで`）、ユーザー自身の言葉に
よる着手の確認として扱い、含まれる書き込みの範囲は gh-issue の「書き込みと承認」に従う。引数に PR が書かれていれば、
PR の名指しにもなる。着手の目印が書かれず PR だけが書かれていても（`#12 PR まで`）、着手の確認にはならない。対話なら、
引数に書かれていないもの（着手の確認、ラベルの作成、「#N の PR を作る」、マージで閉じない Issue をマージの後に
閉じること）を 2. で聞く。ラベルの作成が書かれておらず、`agent:doing` が無いリポジトリでは、gh-issue の「着手する」の
手順 2 に従う。名指しした Issue が sub-issue を持つ親（`view` の `sub_issues` の `total` が 1 以上）なら、`status` に
よらず 2. の「計画の親の番号で呼ばれたとき」に従う。ほかの名指しした Issue の `status` が `ready` でも `external` でも
なく、自分の着手（gh-issue の「着手中か確かめる」）でもなければ、その扱いに従い、着手せずにそう伝える。済ませ忘れか
閉じ損ね（同じ節）に当たる Issue も、着手せずに同じ節の扱いに従う。

非対話では、引数で得た着手の確認の範囲のほかは確認を取れない。ラベルの作成と PR の作成は引数に書かれたときだけ行い、
着手の目印が書かれていなければ Issue には書かない（gh-issue の「途中で終える」の目印を付けずに進める行）。引数が
無ければ、2. の仕分けと組の提案だけを最終応答に書いて終える。そのときの最終応答には、仕分け、組の提案（着手の確認で
聞く中身）、書かなかったこと、確認を挟まずに進めるときの引数の例を書く。番号だけを渡されたら、Issue には書かずに直し、
git-workflow のルール 0 のとおり push まで進め、gh-issue の「途中で終える」に従って最終応答に書く。
計画の親の番号なら、2. の「計画の親の番号で呼ばれたとき」の非対話の行に従う。作業の説明なら、
Issue は立てずに 2. で分けた作業を台帳で持ち、依存の無い作業だけを作業ごとのブランチで push まで進める。依存の
ある作業は先の作業がマージされるまで進めないので、最終応答に計画（gh-issue の「計画として立てる」で問いに書く中身）
と、進めた作業・残した作業を書く。

## 1. 分けてよいかを先に決める

分割は単独で進める場合の数倍のトークンを使い、逐次の作業では精度も落ちる。組が次のどれかに当たるなら分割せず、
組を 1 本のトラックにして、そう決めた理由を 1 行でユーザーに伝える。そのトラックを誰が進めるかは 5. の難易度の表で
決める。分けないときも、Issue の着手・PR・閉じ方は gh-issue に従う。

- 作業の大半が、前の結果を見て次を決める編集とデバッグの連続である
- トラックどうしが同じファイルか、同じ未確定の設計判断に依存する
- 組の全体をメインが一人で進めても、数十回のツール呼び出しで終わる見込みである

どの呼ばれ方でも、作業の中身は 2. で読む（作業の説明なら分解する）まで分からないので、2. で組の案を作ったら、
問い（着手の確認、引数に書かれていないもの）を出す前に組ごとに決める。問いを出さないときも、3. に進む前に決める。
選ばれた Issue が案と違えば、組を作り直して決め直し、問いで見せたトラックの切り方かブランチが変わったら、進める前に
ユーザーに伝える。

## 2. 組を決める

gh-issue skill を呼ぶ。引数が無ければ、その「読む」「着手中か確かめる」「仕分ける」に従ってバックログを仕分ける。
Issue の番号を渡されたら、その Issue を `view` で読む。引数に着手の目印も書かれていれば（計画の親は除く。
下の「計画の親の番号で呼ばれたとき」）、その範囲の着手の確認は済んでいるので、問いは引数に書かれていないもの
（ラベルの作成、「#N の PR を作る」、マージの後に閉じること、ブランチ名など）にだけ出す。作業の説明なら、
下の「作業の説明を分解する」で計画を立てて Issue にしてから、その親の sub-issue のうち `status` が `ready` のものを
着手できる Issue にして、下の箇条で組の案を作る。分けた作業は優先度のラベルが無いので、組は依存の順に作る。

- 着手できる Issue から、優先度の高い順（gh-issue の「優先度と難易度」。ラベルが無ければ中）に、同時に回す組の
  案を作る。Issue の番号で呼ばれたときも、引数に並べた順より優先度の順を先にする。1 組のトラックが 3〜5 本に
  収まる量にし、触るファイルが重なる Issue は別の組に分けるか、1 トラックにまとめる。案の組ごとに 1. を当てる
- `AskUserQuestion` の複数を選べる問いで組を確かめる。これが gh-issue の「書き込みと承認」の着手の確認になる。
  選択肢は Issue にし、説明に次を書く
  - トラックの切り方（1. で分けないと決めたなら、その理由を 1 行）と、ブランチ名の案（git-workflow のルール 1。
    選ばれたらその名前で切る）
  - 優先度（ラベルが無ければ中）と難易度（推定ならそう書く）と、5. で任せるモデル
  - 閉じ方（`Closes` か `Refs` か、マージの後に閉じるか）
  - その Issue への書き込み: 着手の目印（ラベルと着手のコメント）、節目・手放すとき・済んだときのコメント、自分の
    目印を外すこと、「#N の PR を作る」、書き込みに使うラベルが `repo` の `missing_labels` にあれば「ラベルを作る」
  - public か internal のリポジトリなら、ラベルとコメントが読まれること
- 優先度や難易度をラベルにするかは、着手の確認に含めない。ラベルにするなら、Issue と値を並べた別の問いで聞く
  （gh-issue の「書き込みと承認」）
- 情報が足りない・大きすぎる・済んでいそうな Issue、分けた作業が済んだ親（gh-issue の「仕分ける」）と `external` の
  Issue は、組とは別に、提案（質問のコメント、分け方、クローズ）として並べる。どれもそのつどの承認が要る。大きすぎる
  Issue を分ける提案が通ったら、gh-issue の「計画として立てる」で計画を立て、その Issue（親にできなかったときは、
  新しく立てた親）を下の「計画の親の番号で呼ばれたとき」の親として扱う
- 断られた Issue は、gh-issue の「提案から外す」に従う

### 作業の説明を分解する

説明で渡される作業はたいてい大きなひとまとめで、分けずに 1 本で進めると、並べて回せる部分も順に進めることになる。
次の順で分けて計画を立て、計画ごと Issue にする。

- 書き込み先を、gh-issue の「書き込み先」で先に決める（非対話は 0. のとおり Issue を立てない）。「GitHub に書かない」を
  選ばれたら、計画の問いは出さずに、下の「台帳だけで回すとき」に従う
- 完了の条件を決め、触るコードや文書を読んで範囲をつかむ。この段では書き込まない
- 1 本のトラックで終わる大きさの作業に分け、それぞれに完了の条件、触るファイル、依存（先に済ませる作業）、
  難易度の推定を付ける。触るファイルが重なる作業と、前の結果を見て次を決める作業は 1 つにまとめる
- 作業の全体と分けた作業ごとに、gh-issue の「Issue を立てる」のとおり閉じたものも含めて似た Issue を探す。使える
  Issue（gh-issue の「計画として立てる」の、親と既にある Issue の項目）は、その番号で計画に入れる
- 分けて残った作業が 1 つだけなら、並べて回すものが無いので orchestrate は要らない。そう伝えて、次を聞く。
  「Issue を 1 件立てて、その番号で進める」（問いに題と本文の要点を書き、立てた後は Issue の番号で呼ばれたときと
  同じく着手の確認を取る。「GitHub に書かない」の後は出さない）、「Issue を立てずに、orchestrate を使わずに進める」、
  「やめる」。非対話なら Issue を立てずに 1 本のトラックとして進め、最終応答にそう書く。作業がすべて既にある
  Issue で済むなら、それを示し、その番号で呼び直す引数を書く

計画は gh-issue の「計画として立てる」の問いで確かめる。全体の親の Issue と、分けた作業をすべて sub-issue として
立てるので、後の組の作業も GitHub に残り、依存は `blocked` として見える。立てた後の着手の確認は、2. の組を確かめる
問いで別に取る。「立てずに進める」を選ばれたら、下の「台帳だけで回すとき」に従う。組の問いで選ばれなかった
sub-issue も、断られた Issue として gh-issue の「提案から外す」に従う。

### 台帳だけで回すとき

分けた作業を台帳に書き、2. の組を確かめる問いの選択肢を台帳の作業にする（Issue への書き込みの項目は無く、ブランチ名の
案と「PR を作る」を書く）。ブランチは作業ごとに、git-branch のルール 3 でベースから、git-workflow のルール 1 の名前で
切る。依存が済んだとするのは、先の作業がベースにマージされたときである。非対話では、そのうえで依存の無い作業だけを
進める（0.）。組の問いで選ばれなかった作業は、次の組でも聞き直さずに、9. の最終応答に残す。

### 計画の親の番号で呼ばれたとき

sub-issue を持つ親を対象にするときは、親には着手せず、この節で対象と承認を決める。名指しした Issue が sub-issue を
持つ親のとき（0.。前のセッションで計画を立てた親を番号で呼び直したときを含む）と、2. で大きすぎる Issue を分けた
ときが当たる。親かどうかは、gh-issue の「着手中か確かめる」のとおり `sub_issues` の数で見る。

- 親の `status` が `closed`・`skip` か、自分の着手でない `doing` なら、gh-issue の「着手中か確かめる」の扱いに従い、
  sub-issue も対象にせずにそう伝える
- 開いた sub-issue があれば、gh-issue の「計画として立てる」のとおり一覧を読み、開いたものを対象にする。これは対象の
  指定にとどまり、引数の着手の確認、PR の名指し、マージの後に閉じることは sub-issue に及ばない。どれも親を
  名指ししたもので、及ぼすと、ユーザーが見ていない sub-issue（計画の後にほかの人がつないだものを含む）に目印や
  PR が付いたり、閉じられたりする
  - 対話なら、2. の組の問いで sub-issue を選択肢にして、sub-issue ごとに着手の確認を取る。マージで閉じない
    sub-issue は、マージの後に閉じることもこの問いに書く
  - 非対話なら、番号だけを渡されたとき（0.）と同じく Issue に書かずに `ready` の sub-issue を進め、最終応答に
    sub-issue の番号を並べた引数の例を書く
- sub-issue ごとの扱いは gh-issue の「着手中か確かめる」に従う。組の案にするのは `ready` と自分の着手の `doing` の
  うち、済ませ忘れ（着手の後にブランチの PR がマージされた）にも閉じ損ね（`済み:` の後に開いたまま）にも当たらない
  ものだけにする。`external` は 2. の提案に回し、`blocked` は依存の先が閉じるまで待つ。済ませ忘れと閉じ損ねは、
  gh-issue の「着手中か確かめる」に従い、済ませて閉じたら、親の sub-issue を読み直してから組の案を作る。閉じた
  sub-issue に依存していた後の sub-issue は、`blocked` が解けて `ready` になっている
- 呼ばれた時点で開いた sub-issue が無ければ、着手する作業は無い。9. の計画の親の閉じ方に進む

## 3. 台帳を作る

グローバル指示の「判断ログ」のファイルに `## 台帳: <作業名>` の節を作る。会話の要約ではトラックの状態が落ちる
ので、このセッションの状態は台帳を正本にする。ほかのセッションと共有する状態（着手、節目）は Issue に置く。
判断ログのファイルに書けないとき（`~/.claude/` への書き込みを確認する窓口が無い非対話の実行など）は、作業ツリーの
直下の `.orchestrate-ledger.md` に同じ節を作る。`.git/` も `~/.claude/` と同じく保護されたパスで断られるので
使わない。dotfiles の git ロールがグローバルな ignore に `.orchestrate-*` を入れているので、このファイルは
`git status` に出ず、コミットにも stash にも入らない。

- 1 行目: この手順のパス（`${CLAUDE_SKILL_DIR}/SKILL.md`）と、要約の後に Read で読み直すこと
- 呼ばれたときの引数。Read で読み直したこのファイルでは引数が置き換わらず、0. で決まる対象が分からなくなる
- 目標と完了の条件。テストやコマンドで確かめられる形で書く
- 確認済みの事実、未確認の点、仮説（外れた仮説も消さずに残す）
- Issue の一覧: リポジトリと番号、優先度（ラベルか、無くて中か）、難易度（ラベルか推定か）、閉じ方と閉じる承認の
  出どころ、ブランチ、PR、状態。作業の説明なら、親の Issue と、2. で分けた作業ごとの完了の条件・依存も書く（Issue を
  立てずに台帳だけで回すときは、番号の代わりに作業の名前で持つ）
- トラックの一覧: 名前、範囲（触るファイル）、依存、難易度、担当（自分か、subagent の種類と 5. の表のモデル）、
  worktree のパス、状態、停滞の回数、対応する Issue

着手の確認を得た Issue には、トラックを出す前に gh-issue の「着手する」で目印を付ける。

SessionStart フックは、判断ログのファイルが大きいと本文を載せずにパスだけを示す。判断ログのファイルは cwd ごとに
分かれるので、作業の間は `cd` せず、`git -C` と絶対パスを使う。

## 4. トラックに分ける

この節は、分けると 1. で決めた組にだけ当てる。

文脈の境界で切る。機能を作るトラックがそのテストも書き、調べる・実装する・テストする・レビューするの役割では
切らない。役割で切ると引き継ぎのたびに文脈が落ち、調整に作業より多くのトークンを使う。

- 依存があるトラックは直列にし、先のトラックの結果を次の指示文に書き込む
- 書き込むトラックどうしは触るファイルを重ねない。重なるなら 1 本にまとめる
- 1 つの Issue に独立した項目が複数あれば、トラックを分ける
- 組に Issue が複数あるとき、書き込むトラックは Issue ごとに worktree を分けるか、直列にする。PR は Issue ごとに
  分けるので、同じツリーで混ぜると、どの変更がどの Issue のものかを分けられない
- subagent の worktree（`isolation: worktree`）はリモートの既定ブランチから切られ、作業ブランチの未マージの
  コミット（`git log --oneline origin/<既定ブランチ>..HEAD`）を持たない。書き込むトラックを worktree に分けるのは、
  そのコミットが要らないときだけにし、要るなら同じツリーで触るファイルを分けるか、直列にする
- 同時に走らせるのは 3〜5 本までにし、残りは先のトラックが終わってから出す。同時実行の上限
  （`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`）はトラックの中で起こす subagent も数え、達すると待たずに断られ、
  エラーは再試行しないよう指示する。空きが出れば次の起動は通る

## 5. 委譲する

トラックは、難易度に応じたモデルで進める。subagent に任せるときは Agent ツールの `model` に次の値を渡し、台帳の
トラックの行に書く。ユーザーが難易度でモデルを選ぶと決めているので、誰に任せるかはグローバル指示の「サブエージェント」
節の目安より、この表で決める。それ以外の委譲の要件はグローバル指示に従う。

| 難易度         | `model`  |
| -------------- | -------- |
| 難（`expert`） | `fable`  |
| 高（`hard`）   | `opus`   |
| 中（`medium`） | `sonnet` |
| 低（`easy`）   | `haiku`  |

- トラックの難易度は、含む Issue の難易度のうち高いもの（ラベルが無ければ gh-issue の「優先度と難易度」の推定）に
  する。Issue の無いトラック（作業の説明から分けて、Issue を立てずに台帳だけで回す作業）は、2. で付けた難易度の推定を使う
- 分けないと 1. で決めた組の 1 本のトラックは、表のモデルがメインのセッションのモデルと同じ系統（Fable・Opus・
  Sonnet・Haiku の別。バージョンは比べない）ならメインが進め、違えばそのモデルの subagent がメインの作業ツリーで進める
- 分けると 1. で決めた組のトラックは、どれも表のモデルの subagent に出す
- 任せる前に、トラックごとの難易度（推定か）とモデルを 1 行でユーザーに伝える。非対話なら最終応答に書く
- `subagent_type: "fork"` は `model` が効かず、メインのモデルを継ぐので使わない
- どのモデルに任せても、git と GitHub への書き込み、台帳、合流はメインが行う（下の指示文の要件）

指示文には、グローバル指示の要件に加えて次を書く。

- このトラックの範囲と、触らない範囲
- 台帳の確認済みの事実と外れた仮説。書かないと、同じ調査を別の subagent が繰り返す
- git と GitHub への書き込み（add・commit・branch・stash、Issue のコメントとラベル、PR）をしないこと。どれも
  メインが行う。並列の subagent が git に書き込むと index のロックを取り合い、git-workflow を読んだ subagent は
  worktree のブランチを規則外とみなして別のブランチを切る。Issue に書くと、同じ Issue の書き手が増える
- Issue のあるトラックには、その Issue の `agent:doing` はこのセッションが付けた目印であること。gh-issue の着手の手順は
  通らず、Issue には書かない。書かないと、subagent は gh-issue の「着手中か確かめる」に従って作業を断る
- worktree のトラックには、gitignore されたファイル（`node_modules`、`.env` など）が無いこと。依存を入れてから
  試すか、試せなかったことを報告に書く
- ユーザーに聞く判断（設計の分かれ目、範囲の外の変更）が要るところに来たら、推測で進めずに止まり、そこまでの
  状態を報告すること。subagent はユーザーに聞けない
- 返す形: 変えたファイルの一覧、流したテストとその結果、worktree のパス

## 6. 進み具合を見る

報告が届くたびに台帳を更新し、次を確かめる。

- 完了の主張に根拠（テストの結果、diff、コマンドと終了コード）が付いているか。付いていなければ完了にしない
- 同じ調査や同じ失敗を繰り返していないか
- 前進しているか。前進が無ければ停滞の回数を 1 増やし、2 回になったら計画を見直す（範囲を変える、自分で引き取る、
  ユーザーに聞く）

決めたこと、外れた仮説、手放すときの状態のような節目は、gh-issue の「コメントに残すもの」に従ってメインが Issue に
書く。報告のたびには書かない。

## 7. 合流する

合流はメインが 1 本ずつ行い、トラックごとにコミットする（git-commit skill）。

- Issue のあるトラックは、その Issue のブランチ（8. で 1 つの PR にまとめる Issue どうしは 1 本）に合流する。
  ブランチは 2. で決めた名前で、git-branch skill のルール 3 でベースから Issue ごとに切る。前の Issue のブランチから
  切ると、そのコミットを引き連れる。メインの checkout をほかのセッションが使っていれば、`git worktree add` で
  ベースを指定して切る
- 同じツリーのトラックは、そのトラックの diff を読んでからコミットする
- worktree のトラックは、テストが通ったものだけを取り込む。`git -C <worktree> add -A` の後、
  `git -C <worktree> diff --cached --binary` をパッチに書き出し、作業ツリーで `git apply --3way <パッチ>` を
  当ててからコミットする。`git merge` は使わない（git-workflow のルール 8）。パッチは作業ツリーの外（scratchpad が
  あればそこ、無ければ `mktemp -d` で作ったディレクトリ）に書く。外なら、当てた後に取り除く手間が要らない。外に
  書けなければ作業ツリーの直下に `.orchestrate-<トラック名>.patch` として書き、当てた後に `evacuate` で取り除く。
  トラック名は英小文字・数字・`-` にする。空白や `/` が入ると、書き出しが別のパスを指して失敗する
- 合流のたびにテストを流し、壊れたらどの合流で壊れたかを特定してから次へ進む
- コンフリクトは git-recovery のルール 10 に従う

## 8. PR を出して次の組へ

- PR を出す前に、指示文の改訂や複数ファイルにまたがる設計判断を含むなら、グローバル指示のとおり
  `implementation-validator` に見せる。同じものを含むのに PR を出さずに push で止めたブランチは、見せていないことを
  最終応答（9.）に書く。後で PR を作るときに見せるかを、ユーザーが決められるようにするためである
- Issue ごとに git-pr skill で PR を出す。出すのは、着手の確認で「#N の PR を作る」を選ばれた Issue と、ユーザーが
  PR を名指しした作業だけにし、ほかは git-workflow のルール 0 のとおり push で止める。本文の Issue の参照は
  gh-issue の「閉じ方」に従う
- 同じファイルを触る小さい Issue どうしを 2. で 1 トラックにまとめたときは、1. で分けたかによらず 1 本のブランチと
  1 つの PR で閉じてよい
- マージは PR ごとに git-pr skill のルール 11 の承認を得る。着手の確認はマージの承認にならない
- マージで閉じない Issue（`Refs` で参照した、閉じるキーワードが効かない base だった、PR に書かなかった）は、マージの
  後に gh-issue の「手放す・済ませる」に従う。計画に入れた sub-issue と、マージの後に閉じる承認を得た Issue は、
  gh-issue の「閉じ方」のとおりに閉じる。閉じる承認は、gh-issue の「書き込みと承認」の表の、Issue を閉じる行か
  計画としてまとめて立てる行のとおりである（gh-issue の「計画として立てる」）
- 組が終わった後の行き先は、呼ばれ方で決まる。マージ待ちの PR が残っていても、触るファイルが重ならなければ次の組に
  進んでよい
  - 引数無し: gh-issue でバックログを読み直して 2. に戻り、優先度の高い順に次の組の案を作る。ほかのセッションが
    立てた Issue もここで拾う
  - Issue の番号: 名指しした Issue（計画の親を除く）のうち、まだ組に入れていないものが残っていれば、バックログを
    読み直さずに 2. に戻り、その残りから優先度の高い順に次の組の案を作る。前の問いで確かめた Issue は聞き直さない
  - 作業の説明と計画の親: 親の sub-issue を gh-issue の「計画として立てる」のとおりに読み直し、`status` が
    `ready`（依存の先の sub-issue がマージの後に閉じて `blocked` が解けたもの）で、まだ組に入れておらず、
    断られていないものから、2. に戻って次の組の案を作る。依存の先がマージ待ちで `ready` のものが無ければ、次の組は
    無い。台帳だけで回すときは、2. の「台帳だけで回すとき」の「依存が済んだ」で決める
- 次の組が無くなったとき、ユーザーが止めたとき、2 組続けて前進しなかったときは 9. へ進む。組に入れなかった
  Issue（0. で着手しなかった、2. で提案に回した）と、計画に残った sub-issue（`blocked` のまま、着手していない、
  断られた）は 9. の最終応答に書く。残った sub-issue は GitHub に残るので、後で親の番号（`OWNER/REPO#N`）で
  呼び直せば続きから回せる。sub-issue の番号で呼ぶと、その sub-issue だけを回す。台帳だけで回したときは、残った
  作業とその依存を書く

## 9. 終える

- フルのテストスイート（無ければビルドと lint）を流し、台帳の完了の条件と突き合わせる
- 目印を付けた Issue のうち、作業を続けずに手放すもの（push まで届かずに止める、など）は、gh-issue の「手放す・
  済ませる」に従って途中の状態をコメントに残してから目印を外す。PR の名指しやマージの承認を待って止めた Issue の
  目印は外さない
- 計画の親（作業の説明で親にした Issue。立てたものも既にあるものも含む。2. の「計画の親の番号で呼ばれたとき」の
  親も同じ）は、sub-issue が 1 件以上あってすべて閉じていて、本文に残った作業が無ければ閉じる。このセッションで
  計画の問いを出した親はその承認で閉じ、ほかは親を名指しした問いで閉じるかを聞く（前のセッションの承認は使わない。
  gh-issue の「計画として立てる」）。親にしなかった元の Issue が開いていれば、親を閉じるときに、閉じるかを名指しした
  問いで聞く。非対話では閉じずに、最終応答に書く。開いた sub-issue が残っていれば閉じずに、残りを最終応答に書く。
  セッションの後で sub-issue がすべて閉じた親は、gh-issue の「仕分ける」がクローズの提案として拾う
- 台帳の節の見出しに、残った作業や sub-issue が無ければ「（完了）」、あれば「（中断）」を付け、トラックごとの
  結果を残す
- 最終応答に、Issue とトラックごとの結果（PR、閉じたか、目印を外したか。途中で止めた Issue は gh-issue の「途中で
  終える」の報告）、合流したもの・しなかったもの、未確認の点、
  残った worktree のパスを書く。worktree を消すか（`git worktree remove`）はユーザーが決める。作業ツリーの直下に
  `.orchestrate-*`（台帳、取り除けなかったパッチ）が残っていれば、そのパスも書く。ignore されて `git status` には
  出ないので、書かないと残っていることに気づけない

## 対象が 10 を超えるとき

同じ指示を多数の対象（ファイル、パッケージ、URL）に当てる作業で、対象が 10 を超えるなら Workflow ツールの
スクリプトで回してよい。トークンを大きく使うので、回す前に対象の数と見込みのエージェント数を示して
`AskUserQuestion` で確かめる。スクリプトを書く前に workflow-authoring skill を読む。
