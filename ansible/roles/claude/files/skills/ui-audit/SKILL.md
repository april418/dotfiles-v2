# ui-audit

画面が動くか、読めるか、誰の決定でできているかを確かめる手順である。UI を作るときの予防と、既存の画面の点検の両方に使う。

## frontend-design との分担

| やること                                   | 持ち主          |
| ------------------------------------------ | --------------- |
| 配色、書体、レイアウトの方向を決める       | frontend-design |
| 動かない操作部と残骸を見つける             | ui-audit        |
| 表示面積を測り、機能に面積を割く           | ui-audit        |
| 文字、コントラスト、動きを実画面で測る     | ui-audit        |
| 既定値の重なりを数え、誰の決定かを確かめる | ui-audit        |
| 文面と和文の組版を点検する                 | ui-audit        |

方向を決める段階では frontend-design を使う。作る間は下の「UI を新しく作るとき」に沿い、組み上がったら「既存の画面を点検するとき」の手順を流す。

## 考え方

- 1 つのパターンでは判定しない。既定値がいくつも重なると、誰も決めていないように見える
- 一覧は禁止リストではなく、「この選択は誰が決めたのか」を確かめる点検表として使う。答えがブリーフ、ブランド、内容のどれかなら残し、答えが無いものを変える候補にする
- AI 製かどうかは断定しない。測れるのはパターンの有無だけである
- 回避策が次の定番になる。Space Grotesk、クリーム色の背景、大きなイタリックのセリフ見出しはすでに一覧に入っている。避けるための選択にも理由を求める
- 見た目より先に機能の欠陥を見る。見た目の型は人手のサイトとの差が出なかったという小さな測定があり、欠陥は好みに関係なく直せる（[sources.md](sources.md)）

## 直す順番

1. 動かない操作部と架空データの残骸
2. 一覧を優先した表示面積
3. コントラスト、文字サイズ、動きの抑制、フォーカス
4. 見た目の型の間引き
5. 文面と組版

上ほど利用者の作業を止める。見た目の型を先に直すと、消えるはずの部品にも手を入れることになる。

## UI を新しく作るとき

- 本物のデータと件数で組む。架空の例や固定の件数は、そのまま本番に残る
- 未実装の機能の部品は置かない。動かないボタンは、無いより悪い
- 画面の役割を先に決める。ページごとの面積の配分は [area-measurement.md](area-measurement.md) の「判断」にある
- 配色、書体、余白、角丸、動きについて、誰の決定かを 1 行で言えるようにする。言えないものは [visual-patterns.md](visual-patterns.md) の既定値に寄っていることが多い
- 組み上がったら、下の手順の 2〜6 を流す

## 既存の画面を点検するとき

1. 対象を決める。トップ、一覧、詳細、検索、空の状態を最低 1 ページずつ選び、開けないページがあれば書き留める
2. 機能と残骸を点検する（[function-check.md](function-check.md)）
3. 表示面積を PC とスマホの幅で測る（[area-measurement.md](area-measurement.md)）
4. 文字、コントラスト、フォーカス、動きを確かめる（[readability-check.md](readability-check.md)）
5. 見た目の型を数え、誰の決定かを確かめる（[visual-patterns.md](visual-patterns.md)）
6. 文面を点検する（[copy.md](copy.md)）。画面が日本語なら組版も見る（[japanese.md](japanese.md)）
7. 下の「報告の形」にまとめる

## 道具

スクリプトは `${CLAUDE_SKILL_DIR}/scripts/` にある。どれもページとソースの中身を変えない。`area_audit.js` はスクロール位置を先頭へ戻し、`frame` を渡すとページをもう一度読み込む。

| スクリプト          | 使い方                                                                                           | 分かること                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `page_audit.js`     | 中身をブラウザの JS 実行ツールに渡す                                                             | 文字サイズ、コントラスト、動かない操作部、見出し、記号、見た目の型の一部、CSS 規則 |
| `area_audit.js`     | 中身に続けて `await uiAuditArea({item: '<一覧の 1 件のセレクタ>'})` を足して渡す                 | 最初の画面に入る項目の数、一覧と操作部品の位置、見出し領域の内訳                   |
| `count_patterns.py` | `python3 "${CLAUDE_SKILL_DIR}/scripts/count_patterns.py" <src> --exclude <開発用のディレクトリ>` | CSS とマークアップの型の出現数、残骸の候補の `パス:行`                             |
| `contrast.py`       | `python3 "${CLAUDE_SKILL_DIR}/scripts/contrast.py" --fg ink=#1a1a18 --bg paper=#fbfbf9`          | トークンの組のコントラスト比                                                       |

ブラウザのスクリプトは、読み込みと水和が落ち着いてから流す。途中で流すと、動く部品を判定できない。ビューポートの幅が 0 のタブ（非表示のタブ）では `error` を返すので、前面に出すか幅を指定する。

`count_patterns.py` の数は欠陥の証明にならない。偏りを見つけて実画面で確かめる材料である。

## 報告の形

見つけたものを 3 つに分ける。

| 分類                                | 入れるもの                                                                       |
| ----------------------------------- | -------------------------------------------------------------------------------- |
| 残す価値があるもの                  | 製品の内容から来ていて、ほかのサイトに移せない選択                               |
| AI の既定値に見えるので変えたいもの | 誰の決定かを言えない型の重なり。好みの判断なので、変えるかはユーザーが決める     |
| 好みに関係なく直す欠陥              | 動かない操作部、残骸、基準に届かないコントラスト、止まらない動き、件数の食い違い |

- スクリプトの結果は候補である。押すか目で見るかして確かめたものだけを欠陥に書く
- 根拠には `パス:行`、実測値（ページ、幅、ビューポート）、実行したコマンドを付ける
- 未確認の点を分けて書く。開けなかったページ、サインインの奥、押していない操作、目で見ていない折り返しなどである
- 数字を引くときは [sources.md](sources.md) の限界も一緒に引く

## 別のモデルに独立に点検させる（任意）

ユーザーが求めたときに流す。報告が大きな作り直しの判断に使われるときは、流すことを提案するにとどめる。同じ前提に立つと同じ見落としをするので有効だが、費用が増える。

1. 別のモデルの subagent（Agent ツールの `model` で指定する）に、対象の URL かソースのパスと、この skill の点検項目だけを渡す。こちらの結論、実測値、仮説は渡さない
2. 返ってきた指摘を項目ごとに突き合わせ、一致したもの、片方だけのもの、割れたものに分ける
3. 割れた論点は意見で決めず、実測で決着させる。CSS の値から見積もった高さと実画面の値が割れたら、実画面の値を採る
4. 片方だけの指摘は、実画面かソースで確かめてから報告に足す
