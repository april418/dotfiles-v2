# push した後、人に確認を頼む前に

push した後に、人へ動作確認やブラウザでの確認を頼む前に読む。自分が待てば分かることを相手に肩代わりさせない。ユーザーの時間は、機械で代替できない判断にだけ使う。

## CI が green になるまで待つ

PR を作った直後の CI は pending である。pending は「まだ分からない」で、green ではない。CI が green になってから頼む。赤いまま頼むと、相手は動かないものを見せられることになる。

```bash
gh pr checks <number>          # 状態を見る
gh run watch <run-id> --exit-status   # 終わるまで待つ
```

## 相手が開く URL を言えるか確かめる

CI が通ったことと、変更が動いている場所があることは別である。「ブラウザで見てほしい」と頼む前に、相手が開く URL を自分が言えるかを確かめる。言えないなら、それは依頼ではなく丸投げである。

デプロイのトリガーを読む。多くのリポジトリは統合ブランチへの push でしかデプロイしない。

```bash
grep -n -A6 "^on:" .github/workflows/deploy*.yml
```

`on: push: branches: [main]` だけなら、PR の時点ではどこにも反映されていない。この場合に取れる手段は 3 つある。

| 手段                         | 使いどころ                                             |
| ---------------------------- | ------------------------------------------------------ |
| ローカルで preview を立てる  | マージ前に見たい。依存サービスが揃うかを先に確かめる   |
| 先にマージして本番で見る     | 戻せる規模のとき。revert の手順を添えて提案する        |
| PR ごとの preview 環境を作る | 同じ問題が繰り返し起きているとき。別作業として切り出す |

ローカル preview は立てれば見えるとは限らない。ローカルの DB が空、外部サービスのバインディングが本番を向いていない、シークレットが無い、といった理由で空の画面になる。手段を提案する前に、その手段が成立するか（データが入っているかまで）を確かめる。
